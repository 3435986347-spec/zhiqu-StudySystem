# 应用里发起的会话，在命令行里 /resume 接着做（2026-11-17）

用户 2026-11-17：「现在在命令行里发起的会话在应用里能看到，但是在应用里发起的会话，命令行里却看不到。同时最新增加的 memory 功能应用版是否能用得上？我想你出一份方案，让应用版里发起的会话，通过 /resume 在命令行里可以接着继续」。

三件「要你定」用户 2026-11-17 定了（见末尾）。一步一轮做，做完更新「进度」。

## 一句话

两边存的根本不是一种东西：命令行的 `/resume` 读的是**项目文件夹里的完整记录**（`.zhiqu/sessions/<id>.jsonl`，带每一次工具调用和结果）；应用存的是**服务器上的一问一答**（Notebook 里的 `ai_message`：用户原话 + 最终回答 + 给人看的步骤）。命令行 → 应用是单向「抄一份给人看」（`archiveTurn` → `POST /api/harness/sessions/{id}/messages`），反方向没有任何一条路。

而桌面应用的代码模式跑的**就是命令行那一份循环**（`host/code-host.js` → `runTurn`），只是起它时 `store: null` —— 没有会话记录。所以主路很短：**让桌面代码模式和命令行写同一种会话记录、放在同一个 `.zhiqu/sessions/` 里**。记录一有，`/resume` 自然看得见；记忆那几层也跟着全部亮起来（它们都挂在「有会话记录」这个条件上）。

## 现在是什么样（读代码看的）

| | 命令行 | 桌面应用 · 选了文件夹 | 网页 / 应用 · 普通聊天、生成到产物、服务器上的代码模式 |
|---|---|---|---|
| 谁跑循环 | `cli.js` → `runTurn` | 外壳 `LocalAgent.swift` 每一轮起一个 `code-host.js`（本机） → `runTurn` | 普通聊天：后端 Java（`AiServiceImpl`）；代码模式：后端起 `code-host.js` |
| 会话记录 | `.zhiqu/sessions/<id>.jsonl`，完整 | **没有**（`store: null`、`session: { id: 'web-code-agent' }`） | 没有本机文件 |
| 前面的对话怎么带 | 原样的消息（含工具调用） | 页面把最近 40 条问答拍扁成一段「供参考」（`historyBlock`），工具调用、读过什么都没了 | 普通聊天：服务端滚动摘要 + 最近若干条 |
| 存到服务器 | `archiveTurn`：问 + 答 + 步骤，挂在一个新建的「命令行 · …」Notebook（`harness_session` 记着对应关系） | 页面自己存进当前 Notebook | 同左 |

## 记忆功能在应用版里用得上吗

记忆方案（`docs/memory-plan.md`）的 8 步做完了 6 步，**全都只做在命令行这一份循环里**。桌面 / 网页代码模式因为跑的是同一份 `runTurn`，拿到了其中「一轮之内」的那部分；凡是要会话记录的，一样都没有（第一百四十一、一百四十二轮自己写了「桌面 / 网页没有」）。普通聊天走的是 Java，这几步一样都不沾。

| 步 | 内容 | 桌面代码模式（选了文件夹） | 普通聊天 |
|---|---|---|---|
| 1 止血 | 图按张记账、摘要保险、监听泄漏 | **有**（同一份 `agent.js` / `compact.js` / `http.js`）；会话文件图外置用不上（没有会话文件） | 无 |
| 2 工作状态卡 | 压不掉的状态、清单记账、`note` | **半个**：整个文件夹只有一张 `.zhiqu/state.json`，不分会话 —— 同一个文件夹开两段对话，状态卡会串；做完就删，只在「上一轮没做完」时接 | 无 |
| 3 先清再摘 | 可取回的占位 | **半个**：一轮之内能清；大输出存盘（`out/`）要会话记录，没有，占位只能写「重读一遍」 | 无 |

| 6 项目笔记 | `.zhiqu/memory/`、地图、`/memory` | **没有**（`projectMemory` 要 `ctx.store`） | 无 |

所以「应用版能不能用上记忆」和「应用的会话能不能 `/resume`」其实是**同一个缺口**：桌面代码模式没有会话记录。补上它，两件事一起解决。

## 设计

### 会话叫什么：一个 Notebook 对一段记录

- 应用里发起的会话，记录 id 用 `app-<notebookId>`（合 `SessionStore` 的 id 规则 `[A-Za-z0-9_-]{1,64}`）。同一个 Notebook 在同一个文件夹里永远是同一份记录。
- 反方向顺带解决：在应用里打开一个「命令行 · …」的 Notebook 接着说（桌面、选了同一个文件夹），用的是那段命令行会话自己的 id（后端从 `harness_session` 查出来给页面），不新开一份。**两边说的永远落在同一份记录里。**
- 后端 `HarnessSessionService.open()` 认 `app-<notebookId>`：这个 Notebook 是这个用户的，就把 `harness_session` 绑到它上面，不新建「命令行 · …」Notebook。这样命令行接着说的每一轮，存档回到**原来那个** Notebook，应用里打开就在同一个对话里看到。别人的 Notebook 号照旧新建（`requireOwnedNotebook` 判），不泄露、不串。

### 主路：桌面代码模式写会话记录（选了文件夹的）

1. 页面（`sendDesktopTurn`）多给两样：`notebookId`、`sessionId`（新的对话是 `app-<nb>`，命令行来的是它自己的 id）。外壳（`LocalAgent.swift`）照传给 `code-host.js`。**外壳改了要重新打包才到用户手里。**
2. `code-host.js` 的桌面模式开一个真的 `SessionStore(root)`：
   - 记录在 → 用 `store.load()` 的消息（带工具调用，压缩过的照压缩后的）代替拍扁的 `historyBlock`。这一条本身就是质量提升：应用里第二轮终于看得见第一轮读过什么、改过什么。
   - 记录里没有、Notebook 里有的那几轮（中间在普通聊天里说过、在网页上说过）：页面给的 `history` 带消息 id，记录里记一行 `{ type: 'app_sync', upto: <最后一条消息 id> }`，比它新的按现在的「供参考」拍扁追加。只追加，不改前面（缓存）。
   - 记录不在 → 照现在的 `historyBlock` 起头，然后开始记。
3. `archiveDisabled` 保持 `true`：桌面这一轮的问答由页面存进 Notebook，host 再存一份就重了。
4. 状态卡跟着会话走（`sessions/<id>.state.json`），不再用整个文件夹共用的 `.zhiqu/state.json`。旧的那张：没做完的话，第一次开记录时接进来，然后删掉。
5. 于是这些自动亮起来（条件都是「有会话记录、而且就在这个项目的 `.zhiqu/` 里」）：开工给最近三段 + `search_sessions` / `read_session`、项目笔记和地图、大输出存盘、用量进记录、清单记账。不用为应用另写一份。
6. **网页上（服务器跑的）代码模式、生成到产物不做**：文件夹不在用户电脑上，命令行本来也接不过去；它们照旧没有会话记录。

### 命令行这边

1. `/resume`、`--resume`：`app-*` 的记录本来就在 `.zhiqu/sessions/` 里、在 `setup.json` 索引里（host 建记录时同样走 `store.create`，要带上给定的 id），列表里自然出现。标题前标一个「应用」，看得出是从哪来的。
2. **两边轮流说，不能同时说**：一段记录同一时刻只能有一边在跑一轮。跑一轮时拿 `sessions/<id>.turn.lock`（写 pid + 心跳，和 `setup.json` 那把锁一个做法，超过 30 秒没心跳算崩了留下的）。拿不到：命令行说「这段会话应用里正在跑，等它说完」；应用里那一轮直接回一句同样的话。
3. **对方说过了，先读进来**：命令行每一轮开头比一下记录文件的长度，比自己最后写的长 → 别人（应用）接着说过，重新 `load()`，并打一行「应用里接着说了 N 轮，已经读进来」。应用那边每一轮本来就是新进程、从文件读，不用做。
4. 命令行接着说的每一轮照旧 `archiveTurn`，因为上面那条绑定，落在原来那个 Notebook 里。

### 支路：没有文件夹的会话（普通聊天、生成到产物、服务器上的代码模式）

这些在用户电脑上没有记录，只能从服务器取一问一答（用户定了做，列表里写明「只有文字」）：

- 后端两个只读接口（只认个人访问令牌 / 登录令牌，桌面那种 12 小时的不认）：`GET /api/harness/conversations`（最近的 Notebook：标题、更新时间、条数、是不是命令行来的）和 `GET /api/harness/conversations/{id}/messages`（解密后的问答，最多最近 40 条 + 服务端的滚动摘要）。
- `/resume` 列表下面多一段「应用里的会话（只有文字，没有工具记录）」。挑一段 → 在当前文件夹建 `app-<nb>` 的记录，开头一行 `{ type: 'imported', notebookId, upto }`，前面的对话照 `historyBlock` 拍扁放进去（和应用现在给代码模式的同一个口径，照实标「当时的，要用工具重新查」）。之后就和主路一样：命令行接着说，存档回原 Notebook；之后在桌面应用里选这个文件夹接着说，用的也是这份记录。
- 桌面应用在同一台电脑上：host 建记录时顺手在用户级的 `~/.zhiqu/app-sessions.json` 记一行「Notebook → 文件夹」（只在本机，不上传绝对路径）。命令行在别的文件夹里 `/resume` 选中它时，说「这段在 `~/proj` 里，`cd` 过去再 `/resume`」，而不是在错的文件夹里导一份文字版。

## 要你定（用户 2026-11-17 定了：「按你的建议定」）

1. **没有文件夹的会话也能 `/resume`**（第 3 步做），列表里写明「只有文字」—— 服务器上本来就没存工具调用。
2. **两边都能开着同一段会话，一次只有一边在跑一轮**（锁）；后说的那边先把对方说的读进来。
3. **记录 id 用 `app-<notebookId>`**（「默认对话」没有 Notebook 号，用 `app-default`）。

## 不做的

- 服务器上跑的代码模式、生成到产物：文件不在用户电脑上，命令行本来就接不过去。
- 不把完整工具记录传到服务器：存档只给人看（现在的约定），完整记录留在用户自己的项目里。
- 不改普通聊天（Java 那一路）的记忆：它有自己的滚动摘要和长期记忆，记忆方案第 7 步（用户记忆逐条）会把两边的用户记忆统一，这份不碰。
