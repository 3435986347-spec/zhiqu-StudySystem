# 项目锐评：2026-11-10

> 这是对工作区当前 checkout 的一次快照评价，不是一轮开发记录。行数、路由数、迁移号、缓存令牌这些数字会随后续改动变化；结论里的结构性问题比具体数字更值得看。
>
> 评价范围：后端、前端、测试与交付、产品聚焦。没有逐页打开浏览器看视觉，前端「设计」一项只针对设计系统与 CSS 纪律，不针对像素。

## 一句话结论

这是一个**「防线比产品更完整」**的项目：安全、并发、失败路径、判据纪律都做到了商业项目水准；但它也已经走到「复杂度本身成为最大风险」的阶段。

综合 **7.5 / 10**：工程纪律 9.5，安全边界 9，前端设计 8.5，前端工程 6，后端可维护性 5.5，交付运维 4，产品聚焦 5。

## 规模先摆出来

- 后端：353 个 Java 文件 / 42,848 行。
- 测试：262 个文件 / 41,606 行 / 1,396 个 `@Test`；其中 39 个类用 Testcontainers。
- 前端：14,616 行（HTML/CSS/JS），15 个页面，9 个页面模块。
- 接口与数据：22 个 controller、约 199 个路由映射、48 个 Flyway 迁移、约 55 张表。
- AI / 知识 / 工作区 / RAG 相关：约 2.6 万行，占后端六成。
- 命令行：约 1 万行，48 个 JS 文件。
- 文档：2.1MB；`docs/rounds/` 1.2MB。

它早就不是「小项目」了。

> 数字口径：行数用 `wc -l`；路由用 `@GetMapping` / `@PostMapping` 等注解计数（含类级 `@RequestMapping`，所以是「约」）；测试数用 `@Test` 出现次数；表数用迁移里的 `CREATE TABLE` 计数；`Map<String, Object>` 是字面量出现次数；Docker 状态是写这份文档时 `docker info` 的结果。

## 先说值得尊敬的

这些夸赞不是客套，很多商业项目都做不到：

- **测试纪律**：测试代码几乎和主代码一样多（41,606 行 vs 42,848 行），而且强调「新判据要见过红才算数」、`Failures` 和 `Errors` 要分开看、扫空和扫干净长得一样。这是被坑过才会有的自觉。
- **安全边界**：工作区默认关闭、`requireLocal()` 挡 DNS 重绑定、主密钥哨兵、`StartupSecretGuard` 拦仓库里的开发默认值、SSRF 校验放在真正发请求的那一层、JWT epoch 改密即失效、SameSite=Lax + HttpOnly。这不是「加个 JWT」的水平。
- **失败路径**：幂等键、乐观锁、心跳/租约、输出上限、DeepSeek 默认思考、流式请求的装配窗口、几个后端共用一个库的认领。代码里到处是「原来这里是错的」的注释，而且都能对上测试。
- **设计系统**：一套令牌、浅深两套、焦点环、`prefers-reduced-motion`、图标集、页面头部统一、骨架先露。前端不是乱，是有纪律的。
- **文档**：128 轮、2.1MB，把「为什么」留下来了。`CLAUDE.md` 被压到 200 行，说明作者知道上下文预算。

## 前端：设计是 8 分，工程是 6 分

- **「无构建」已经变成「手工构建」**：缓存令牌在 15 个 HTML 里出现 **99 次**，每次改静态资源都要手改一遍；另外还有 68 个 node 判据、源码扫描测试、样式棘轮。这不是「没有工具」，是把工具分散到了纪律和测试里。一个 30 行的 esbuild 脚本就能把令牌注入、模块打包、压缩全做掉。**无框架可以，无工具不必。**
- **两套模块系统**：`zhiqu-api.js` 是 2,775 行的经典脚本 + `window.ZQUI`，页面是 ES 模块，接口靠 `zqShared` 和 `PageModulesTest` 扫名字。能用，但契约不在类型里，在字符串和测试里。
- **两个页面巨兽**：AI 助手 2,837 行 + 知识 Wiki 1,964 行，占 9 个页面模块的 **77%**。Wiki 是一个披着页面外衣的编辑器产品（CodeMirror、表格、公式、自动保存、乐观锁），AI 助手是聊天 + Notebook + 产物 + 执行轨迹 + 模型设置。两者都该再拆一层内部模块，而不是继续在一个文件里长。
- **体积与带宽**：`zhiqu-api.js` 176KB、CSS 159KB、AI 页面 150KB、KaTeX 592KB。线上 1.5Mbps 的瓶颈你们已经撞过（第一百二十轮）。现在靠压缩、Service Worker、懒加载顶着，但**没有 bundle size 预算**，下次再加一个编辑器/图表就又回去了。
- **测试是源码断言，不是视觉/可访问性**：`*LookTest`、`*WiringTest`、`InlineStyleRatchetTest` 很聪明，但它们测的是「代码长什么样」，不是「用户看到什么」。首页轮播截图是唯一的视觉回归，其他页面改坏了只能靠人眼。没有 axe/Lighthouse 一类的自动检查。
- **业务错误 HTTP 200 + `code != 200`**：前后端一致，但代价是所有通用工具（监控、网关、重试、SDK）都失去判断力；前端必须同时处理 HTTP 错误和业务 `code` 两套通道。这是十年前的 Java 企业习惯，不是错，但很贵。

## 后端：单体是对的，「模块化单体」只做了一半

- **`AiServiceImpl` 是事实上的内核**：4,758 行、约 160 个方法、20 多个内部 `Runner`。这不是「文件大」，是「没有边界」。它同时管流式、多 agent 编排、检索、计划、Wiki、代码、记忆、校验、总结。文档里说拆过，但数字说明它又长回来了。应该拆成 orchestration kernel + 各 stage 类，并加一条文件行数/依赖方向的门禁。
- **API 没有类型**：`Map<String, Object>` 在主代码里出现 **1,216 次**，**91 个**控制器方法返回 `Map<String, Object>`，DTO 只有 **10 个**。字段名就是契约，前端/CLI/桌面三个客户端靠字符串和测试对齐。这是后端最大的可维护性债，比 `AiServiceImpl` 还难还。先给 CLI/桌面用到的 20 个接口加 `record`，再谈大重构。
- **约 199 个路由、55 张表、48 个迁移**：包名分了 `controller/service/mapper`，但服务之间没有 ArchUnit/边界检查，`AiServiceImpl` 可以调用一切。单体没错，错的是「模块化」只停留在目录名上。
- **一个具体的裂缝**：`StudyTaskServiceImpl.update` 用 `updateById` 整份写回，而 MyBatis-Plus 默认跳过 null。前端把「清空截止时间 / 开始时间 / 提醒时间 / 描述」发成 null，到这里就被跳过——**清空不会落库**；`updateStatus` 把已完成改回未完成时，`completed_at` 也不会清空。你们自己的 `CLAUDE.md` 就写着这个坑，代码里没加 `updateStrategy = ALWAYS`，测试里也没有「清空」的判据。建议先补一条集成测试，再修。
- **搜索是解密后全扫**：任务标题/描述加密存，搜索只能取最多 5,001 行、全部解密再过滤。几千条任务几十毫秒，十万条就是灾难；超过 5,000 条还会告诉用户「只在前 5,000 条里找」。隐私和搜索只能二选一，或者上盲索引/全文索引。
- **业务错误统一 `code=500`**：`Result.fail` 把所有 `BusinessException` 都变成 500，HTTP 仍是 200。用户输入错和服务器炸在监控里长得一样，Prometheus/网关分不出来。
- **JVM 里嵌了一个 Node**：代码 agent 起 node 跑 `zhiqu-cli/src/host/code-host.js`，JAR 里带 CLI 源码，服务器装 Node，Mac 包装 Node。把两份循环合成一份是勇敢的决定，但代价是一个 Java 单体多了第二个运行时、第二套测试、第二套部署依赖。
- **RAG 是第二个系统**：4,471 行 Java + Python/FastAPI/Chroma + outbox + 蓝绿重建 + worker。它可选、连不上会退回关键词——那它值不值这个复杂度？如果语义检索不是卖点，这是最该砍的一块。
- **Redis 掉了会静默退回进程内**：锁、幂等、限流都这样。单机开发没问题；几个后端共用一个库时，这是重复提醒/双写的静默路径。生产要么强制 Redis，要么启动时大声拒绝，不能悄悄降级。
- **没有 actuator / health / metrics**：主服务没有 `/actuator/health`，没有 Micrometer；RAG 有 `/health/live`，主服务没有。线上排障靠日志和自定义后台。这是运维上最薄的一环。

## 交付与文档：最弱的一环

- **没有 CI**。没有 `.github/workflows`，没有 Jenkinsfile；1,396 个测试靠本地自觉。Docker 现在没开，39 个 Testcontainers 类要么报错要么跳过；不管哪种，`BUILD SUCCESS` 都不能当成集成测试跑过了。**这是全项目 ROI 最高的一处**：一个 workflow 就能把「作者记得」变成「合并前必须绿」。
- **没有 staging/灰度**：部署脚本从开发机直接上，`zhiqu_verify` 是手工验证库。一个人维护可以理解，但公开服务没有回滚演练。
- **档案维护得比门面好**：文档 2.1MB、128 轮，`ClaudeMdTest` 甚至管着 `CLAUDE.md` 不超过 200 行；但前门 `README.md` 还写着 V20，`AGENTS.md` 写着 V36，实际 V48。新 agent 读的是门面，不是档案。
- **一堆「以前留下的」**：`static/vendor/` 是 6 个占位桩（最大的 1.3K），还留在放行清单里；根目录 `zhiqu-ui/` 是 9 月 2 日的旧副本；`rbody.json` / `vbody.json` 是探针请求体；`CORS` 只放行 `localhost:5173`。它们不致命，但让「哪些是活的」需要考古。
- **5 种运行时**：JVM、Node、Python、Swift、浏览器；Mac 薄客户端、Windows 胖后端；Ubuntu/Windows 两条部署路径。每加一个功能，都要问「这条路径在几个运行时上成立」。

## 产品：五个产品挤在一个壳里

任务/例行/提醒、成就/参考计划、知识 Wiki、AI 聊天、编码 agent/工作区、RAG——至少五个产品。学习系统的 DNA 还在：`StudyTask`、`study_record`、`create_study_plan`、成就系统、参考计划社区。如果今天从零做「AI 办公助手」，你会保留成就系统和参考计划吗？

CLI 是最差异化的部分（Codex 同级、子 agent、沙箱、`exec`/`review`），但它和办公助手是两条产品线。两条都做，就会都做不深。

## 如果只做五件事

1. **加 CI**：MySQL/Redis service + `mvn -o test` + `npm test` + 构建；`Skipped` 不算通过。没有 CI，前面所有纪律都只是「作者记得」。
2. **补账号生命周期**：密码最小长度、自助找回、邮箱验证（可选）、自助注销、隐私政策/用户协议。公开注册 + 备案号 + 没有这些，是产品底线问题，不是代码洁癖。
3. **修 `updateById` 清空字段 + 加健康检查/指标**：先补「清空截止时间」的集成测试；再上 actuator health、Micrometer，Redis 不可用要大声报错或拒绝启动。
4. **消灭手工缓存令牌**：一个脚本统一替换 15 个 HTML + Service Worker，再加一个「令牌必须变化」的检查；顺手用 esbuild 做最小打包/压缩，保留无框架。
5. **类型化 API + 拆 `AiServiceImpl`**：先给 CLI/桌面用的 20 个接口加 record，再按 Runner 拆 stage 类；用 ArchUnit/文件行数门禁防止再长回去。

另外三件便宜但值得做：修 `static/vendor`/`zhiqu-ui`/`rbody` 这些死文件；把 RAG 降级成可选插件或砍掉；想清楚「办公助手」和「编码 agent」到底做哪一个。

它不是烂项目，恰恰相反：它的防线比大多数商业项目都多。问题是它把「不出错」做到了极致，还没把「少做事」当成一种能力。下一轮最值得做的，可能不是再加一个功能，而是删掉一个运行时、一个旧目录、一个 god class、一条产品线。
