# 第一百二十二轮（2026-11-08）：RAG 跟着后端一起起来、默认开着

## 由来
用户：「同时rag要和后端一起启动，默认启动，每个人的rag都不一样」「网页上的rag我点击构建服务一直卡在building」。

现状：
- 后端仓库里的默认就是开着的（`app.rag.enabled: true`，连不上旁路时退回关键词检索）；线上关着，是第一百一十九轮部署时没装旁路、我关的。旁路（`rag-service/`）没装。
- 「重建索引」什么都不查：直接建一个 BUILDING 的新代次、排一个要旁路才做得了的作业；领作业的后台进程跳过要旁路的活 —— 于是永远 building。
- 每个人分开：旁路里每一条索引都带 userId，查的时候按 userId + 资料编号过滤，后端按用户取检索范围。本机实测：用户 2 拿用户 1 的资料编号查「项目代号」查不到，查自己的查得到。
- 本机量旁路（macOS、torch CPU、bge-small-zh-v1.5）：7 秒起来，起来就 407MB，建了索引 470MB。服务器 2 核 1.9G，还能腾出约 930MB。
- 依赖钉在 Python 3.11 那一套（torch 2.5.1、numpy 1.26、chromadb 0.6.3），服务器自带的是 3.14，装不上；torch 默认的 Linux 版会把几 GB 的 CUDA 库一起拉下来；服务器在国内，PyPI / GitHub / HuggingFace 都慢或断。

## 计划
1. **重建索引先看旁路**：旁路没开、连不上、没准备好 → 直接说原因（「现在检索退回关键词」），不建代次；已经有一个在重建 → 说那一个的进度，不再叠一个。
2. **服务器上跟着后端起**：`zhiqu-rag.service`（`zhiqu` 账号、只听 127.0.0.1:8001、内存上限、torch 一个线程、读不到别的）；后端的单元 `Wants=` 它（一起起，不等它：它没起来时后端照旧退回关键词），它 `PartOf=` 后端（一起停、一起重启）。生产配置的 `rag.enabled` 改成 true；令牌用第一百一十九轮安装时生成的那一个（从配置里读，不打印）。
3. **离线装**：在开发机上把 Linux x86_64 的 Python 3.11、只要 CPU 的 torch 和其余依赖的 wheel、模型（带 revision 标记）打成一包，传到服务器离线装 —— 服务器上一个字节都不从外网下。`deploy/ubuntu/rag-from-dev.sh` 一条命令（往线上推这一步被权限系统拦过，用户自己跑）。
4. **装之前先在 amd64 的容器里装一遍**（和服务器同一个架构、同一个 Ubuntu 版本），起旁路、建索引、查一次、量内存；容器要带 `--pids-limit`、`--memory`。
5. **每个人分开**：后端这一层补一条端到端（两个用户、各自的资料，查不到对方的）。
6. 桌面版：不在每台电脑上再起一份旁路（要带上 1GB 的 torch）—— 用户定了桌面版改成登录网站、数据走网站，RAG 跟着数据在服务器上。
7. 部署后在线上看：旁路 ready、后端的状态页说 ready、卡着的那个代次被领走做完。

## 结果

- **重建索引先看旁路**（`RagAdminService.rebuild`）：旁路没开 / 没令牌 / 连不上、没准备好 → 照实说（「现在检索退回关键词，重建要等旁路起来。服务器上看 systemctl status zhiqu-rag」），不建代次；已经有一个 BUILDING → 说它的进度（#id、x / y），不再叠一个。线上卡着的那一个不删：旁路起来之后被领走接着做。
- **每个人分开**（后端这一层，`RagRetrievalUnitDialectBaselineTest#每个人只查得到自己的`）：两个用户各有资料和 Wiki 页、在同一个索引代次里；各自去查时交给旁路的 userId 和资料编号只有自己的；旁路就算错把别人的候选交回来（桩故意这么做），后端也不放进上下文；拿别人的笔记本编号、点名别人的资料都拒，旁路一次都不问。旁路那一层本机和容器里都真跑过：用户 2 拿用户 1 的编号查不到。
- **服务器上跟着后端起**：`deploy/ubuntu/zhiqu-rag.service`（zhiqu 账号、只听 127.0.0.1:8001、`IPAddressDeny=any` 出不了网、`HF_HUB_OFFLINE`、只写得了 `data/rag`、torch 一个线程、内存 850M 压着 / 1000M 封顶、`PartOf=` 后端）；后端的单元 `Wants=` 它、不 `After=` 它（不等它）；模板里 `rag.enabled: true`。
- **离线装**：`rag-from-dev.sh` 在开发机上打包（python-build-standalone 3.11.16 钉地址和 sha256、wheel 105 个 317MB、torch 是 `2.5.1+cpu`、一个 CUDA 库都没有、测试用的 pytest 不带、模型 183MB 带 revision 标记；共 531MB，留在 `build/rag-bundle`，依赖没变不重下；`RAG_BUILD_ONLY=1` 只打包）。`install-rag.sh` 在服务器上离线装（`--no-index`）、Python 先校验再解开、令牌和索引版本照后端的配置抄（不打印）、`rag.env` 写的时候就是 640、配置只翻 `rag.enabled` 一个值并先留备份、等旁路 ready 再重启后端。索引版本照抄后端配置里的原值（模板里是 `…@PINNED_REVISION-…` 这个占位写法）：改了的话线上卡着的那个代次就对不上了；模型版本另有 revision 标记那一道。
- **amd64 的容器里装了一遍**：Ubuntu 26.04 的 tar 在这台 Mac 的 amd64 模拟（Rosetta）里往子目录解就报「Function not implemented」（Ubuntu 给 tar 打的安全补丁用了 openat2，Rosetta 不支持；真服务器是原生 x86_64，不受影响），换 amd64 的 Ubuntu 24.04 装：离线装好、torch 2.5.1+cpu、配置和原来只差 `enabled` 那一行、`rag.env` 和配置都是 640 root:zhiqu、令牌两边一致；用 zhiqu 账号照单元里的环境变量起旁路：4 秒 ready、索引版本两边一致、用户 2 拿用户 1 的编号查不到；内存起来 600MB、查完 672MB（比 Mac 上多），上限从 800M 调到 850M 压着 / 1000M 封顶。试装第一遍还撞到两处是我测试脚本的错：容器里没给 zhiqu 开 `/home/ubuntu` 的「穿过」（服务器上 `install.sh` 用 ACL 开过），核对配置时把别处的 `enabled: true` 也换了。
- 判据：重建的两道（真库 + 单元）、每个人分开（真库 + 桩旁路）、部署的单元 / 模板 / 安装 / 打包（`UbuntuDeployTest` 两条）。扰动 28 个全红（第一批里「rag.env 谁都能读」是绿的：判据只查了有没有 `0o640`，改配置那一步也写着；而且最后还有一句 chmod —— 两道各查各的之后都红了）。
- 桌面版不另起一份旁路：用户定了桌面版改成登录网站、数据走网站，RAG 跟着数据在服务器上。
