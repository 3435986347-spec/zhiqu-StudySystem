# 第二十八轮（2026-10-04）：几个后端连同一个远程库

## 由来
用户 2026-10-04 说明部署形态：**桌面应用和网页端都连服务器上的同一个 MySQL**（现在实际连的是本机 Homebrew 的 MySQL，目标是远程）。
于是会同时有好几个后端进程写同一个库：服务器上一个、每台开着桌面应用的电脑上各一个。第二十七轮收尾时查出三处「假设只有一个进程」，
用户选了「先修这个，再做 MCP」。

1. **加密主密钥不一致会把数据写坏**。桌面应用没有覆盖 `app.crypto.master-key`（`application-desktop.yml` 里没有、README 的模板里也没写，
   从 Finder 打开的应用也拿不到 shell 里的环境变量），用的是仓库里的开发默认值；服务器的生产配置不许用它。连到同一个库上：
   桌面应用解不开服务器写的密文（任务标题、Wiki 正文、模型 Key），它写进去的又是用一把公开的密钥加密的，服务器反过来也解不开。
2. **启动时收拾「没做完的事」会掐掉别的进程正在做的**。`InterruptedWorkRecovery` 只认「这个进程启动之前建的行」——
   桌面应用一启动，服务器上正在生成的回答就被收成「服务在回答途中重启了」。
3. **早上 8 点的汇报每个实例各发一遍**。任务提醒是逐条原子认领的（不会重复），但汇报里例行计划那部分不认领，靠的是一把锁 ——
   没有共享 Redis 时那把锁只在本进程有效。

## 计划（开工时）

1. **主密钥哨兵**（V43 `crypto_canary`）：启动时用本进程的主密钥解库里的哨兵，解不开就**不启动**并说清楚
   （「这台机器的加密主密钥和这个数据库里的数据不是同一把；连同一个库的所有实例必须配同一把，桌面应用在 `~/.zhiqu/application.yml` 里配」）。
   库里还没有哨兵时，先抽查已有的密文（`CryptoKeyRotation.TABLES` 每一列抽几格）：一格都解不开就不启动、也不写哨兵 ——
   否则一个配错密钥的实例先启动，就把哨兵写成了错的那把，正确的那台反而起不来。全空的新库才写哨兵；两个实例同时写，以先写进去的为准、再核一次。
   哨兵加进 `CryptoKeyRotation.TABLES`，轮换主密钥时一起换。README 的模板加上这一行。
2. **心跳代替「启动之前」**：回答（`ai_message`）和执行记录（`ai_agent_run`）加 `heartbeat_at`（V43）；一轮进行中每 30 秒用**数据库的钟**
   碰一下（不同机器的钟对不齐，数据库只有一个）。收拾的条件改成「进行中、而心跳停了 3 分钟以上」—— 不管是哪个进程的；
   步骤和任务跟着它们的执行记录走（执行记录不在进行中了，它下面还在进行中的就是遗留）。启动时一趟，之后每 2 分钟一趟。
   卡死的线程会一直心跳 —— 所以心跳最多跳 30 分钟。
3. **一天一次的定时任务按天认领**（V43 `scheduled_job_claim`，主键 `(job, slot)`）：8 点那一趟先 `INSERT IGNORE` 一行
   「daily-reminder / 那一天」，插进去的那个实例才发，别的跳过。不依赖 Redis。

### 怎么验
判据：哨兵（新库写、同一把过、另一把拒、没哨兵但已有别人的密文时拒且不写、两个实例抢着写）、轮换覆盖哨兵；收拾（别的进程正在跳心跳的不动、
心跳停了的收、旧行没有心跳按建立时间算、执行记录收了之后它下面的步骤和任务跟着收）；8 点的认领（同一天第二个实例不发）。
真机：两个后端（不同端口、不同主密钥）连 `zhiqu_verify`，第二个起不来并说出原因；同一把主密钥的两个后端，一个在生成回答时另一个重启，回答不被掐。
扰动见红；全量通过；桌面应用重新打包（README 模板）。

## 结果（2026-10-04）

照计划做完：V43（`crypto_canary`、`ai_message` / `ai_agent_run` 的 `heartbeat_at` 和状态索引、`scheduled_job_claim`）、
`CryptoKeyCanary`（bean 初始化时核 —— 在迁移之后、Tomcat 接请求之前）、`StreamLiveness`（心跳）、`InterruptedWorkRecovery` 改成看心跳并每 2 分钟一趟、
`ScheduledJobClaims` + `ReminderScheduler` 早上那一趟按天认领、README 模板加主密钥那一行和「几个后端连同一个库」一节。

**判据先红出来的**：
- **钟**：第一版「心跳停了」写成 `COALESCE(heartbeat_at, created_at) < NOW() - 3 分钟` —— 集成判据当场红：`created_at` 是 JVM 按业务时区写的，
  而数据库会话时区只在 `main` 里钉成业务时区，测试里差 8 小时，5 分钟前建的行在数据库眼里还在将来。改成每个时间跟写它的那个钟比：
  心跳跟 `NOW()` 比，没有心跳的旧行的 `created_at` 跟 JVM 算的截止时刻比。
- **第一次心跳**：原来交给定时线程（延迟 0），一轮很快的回答可能在第一次心跳之前就结束了 —— 改成 `hold()` 当场碰一次。
- 「明文不算数」那条判据第一版撞了唯一键（一个人一个 `conversation_key` 只有一段对话），是判据的错，改用两个 key。

**判据**：`CryptoKeyCanaryIntegrationTest`（6：启动时写了哨兵、另一把不启动并说清楚去哪配、没哨兵时先核已有密文且不写、新库先到先得、明文不算数、轮换覆盖哨兵）、
`InterruptedWorkRecoveryIntegrationTest`（新 3 条：看心跳不看启动时间〔连同活着的执行记录下面的步骤 / 任务〕、心跳〔当场碰、只碰进行中的、定时收〕、按天认领）、
`ReminderClockTest`（别的实例认领了就不发）、`AiConversationLifecycleIntegrationTest`（一轮回答进行中有心跳）。扰动 14 个全红。

**真机（两个后端连同一个 `zhiqu_verify`）**：
- 另一把主密钥的后端：退出码 1，日志里是「这台机器的加密主密钥……不是同一把……这次不启动」，Tomcat 没开（端口没监听）。
- **对照组**：后端 A 正在生成一条回答（还在等模型的第一个字），途中启动**第二十七轮的旧代码**（桌面包里那份）—— 它一启动就把 A 正在生成的回答收成了 ERROR
  （日志「回答 1 条」，4 秒后查库已是 ERROR，远早于 60 秒的等待上限）。对照组死了，实验才算数。
- **实验组**：A 生成一条 90 秒的回答，第 13 秒启动新代码 —— 收拾了 0 条，A 的回答照常写完（DONE、90 段一段不少、没有错误）。
- 做实验时踩的两个坑（都在验证脚本里，不在产品里）：假模型用了 `req.on('close')` 停定时器 —— Node 里请求体一读完它就触发，模型一个字没吐，
  A 等了 60 秒放弃；第一次实验组两个后端只重叠了 2 秒（两次工具调用之间隔了二十几秒），不算数，把回答拉长到 90 秒重做。

**验**：全量 940 / 0 / 0 / 0（第一遍 1 条红：`CryptoKeyRotationRunnerIntegrationTest` —— 测试上下文是用开发默认值起的，哨兵也是它写的，在「旧 key → 新 key」的轮换眼里成了「第三方 key 的一行」。真实部署里哨兵和别的密文是同一把写的，判据照这样摆好，并改成断言「轮换后哨兵用新 key 解得开」—— 把哨兵从轮换清单里拿掉，它红）。桌面应用重新打包（README 模板在仓库里，不在包里；包里的是新的哨兵 / 心跳 / 认领代码）。

**还没做**：桌面应用真的连上远程库之前，用户要在 `~/.zhiqu/application.yml` 里配上和服务器一样的主密钥（README 有模板）。
认领了早上那一趟的实例做到一半没了，那天例行计划的提醒没人补（任务提醒自己有重排）。
