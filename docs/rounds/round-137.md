# 第一百三十七轮（2026-11-15）：记忆第 1 步 —— 止血

方案在 [`docs/memory-plan.md`](../memory-plan.md)，这一轮做它的第 1 步：都是坐实的错，不涉及要用户定的事。

## 由来

用户给了一段真实的命令行记录（做游戏，`~/Desktop/历史记录.txt`）和它的会话文件，要我看记忆机制的不足。量出来的：

- 23 小时、1M 的窗口，**压缩了 105 次**，每次压完只剩「摘要 + 一句好的 + 最后一张截图」；
- 11 次摘要是空的（原文「（摘要为空）」），照样把历史全换掉；69 次摘要里写着 `[object Object]`；
- 同一个文件读了 503 次；任务清单整份重列 6 次，结束时 0/8；
- 跑到 8.4 小时进程内存爆掉（4GB）；会话文件 555MB，`/resume` 读不回来。

## 改了什么

| 病 | 根因 | 改法 |
|---|---|---|
| 一张图几十万 token | `compact.js` 对不是字符串的内容 `JSON.stringify` 再数字，base64 全算进去（1MB = 39 万）。服务端第一百三十四轮改成了按张，这一份没跟 | `estimateContent`：图按张（`IMAGE_TOKENS` 1200，和 `HarnessContext` 同一个数）。两边用同一份样例 `zhiqu-cli/test/fixtures/token-estimate.json` 对拍 |
| 一张大图就「对话内容太大」 | 网关 `validMessages` 的总字数把 base64 算进去，6.8MB 的图 932 万字 > 800 万 | `textChars` 不算图；图另限 40 张、单张约 8MB |
| 每次请求把大图整张再传 | 截图是 PNG、不缩不压 | `forContext`：超过 400KB 的缩到长边 1280、转 JPEG，还大再降档（macOS 用 `sips`，别处找 ImageMagick）；压不了的 1.5MB 以内原样给，再大照实说。8MB 的上限留给截图本身 |
| 空摘要进历史 | 摘要那次调用跟着 `/effort max` 思考，上限 4096，额度想完正文是空的 | 明说 `instant`、上限 12000；`summaryProblem` 校验，空的重来一次，还空就**不替换历史**、只省略旧工具输出、告诉用户 |
| 摘要把提醒当成用户的话 | 命令行补的 user 消息一律标【用户】，带图的变 `[object Object]` | 标【系统提醒】，图写成〔截图〕；摘要的规矩里说清「任务清单是助手自己列的」 |
| 压完只剩最后一张图 | 「最近一轮」按 user 角色切，命令行补的 user 消息也算一轮的开头 | `splitRounds`：用户真说的一句、模型的一次回复各算一步；留下的从助手开头时不垫那句「好的」 |
| 压完还超、一轮一压 | 没有出路 | 压完还超就把最大的工具输出 / 提醒换成占位（`shedLargest`）；连着 3 轮都在压缩就停下说明 |
| 内存爆掉 | `http.js` 给这句话的中断信号挂监听、用完不摘；监听攥着请求，请求的回调攥着整份请求体 | 请求 `close` 时摘掉；`sleep` 同理 |
| 会话文件 555MB、读不回来 | 图以 base64 存在每条消息里，每次压缩再存一遍；`readFileSync` 整个读成一个字符串 | 图存成 `sessions/<id>/blobs/` 下的文件（按内容取名），记录里只留引用，读回来换回去；`eachLine` 一行一行读；旧格式照样读 |
| 用户记忆满了悄悄截掉 | `appendItems` 合并后取前 2000 字，新条目在最后 | `mergeItems`：放不下就拒绝并说清楚，一条都不写 |

顺带：按「一步」切之后，被压掉的那段里会有后来补的话，「用户原话」的预算先被它们占掉、最早那句要求反而没了（`review.test.js` 照出来的）—— 原话改成**第一句永远留着**，超预算丢中间的。

## 判据

- `zhiqu-cli/test/memory-accounting.test.js` 11 条；后端 `HarnessImageAccountingTest` 3 条、`LongTermMemoryMergeTest` 2 条。
- 样例照那段真实会话的节奏造（每 12 步一张 1MB 的图）；真实的会话文件是用户的聊天记录，不进仓库。
- **扰动 25 处全部见红**（命令行 21、后端 4），都恢复了。改了期望的旧判据 3 条：`mcp-compact`（按步切之后留下的多一条）、`complex-tasks` 的原话预算（丢中间的，不是最早的），理由写在判据旁边。

## 顺带修的一条老红

评测工具那组（`node --test tools/benchmarks/*.test.mjs`）在干净的基线上就有 1 条红：第一百三十五轮起 `preview_page` 只在这台机器找得到浏览器时才下发，
评测的工具表跟着机器变（有 Chrome 的电脑上多一个工具）。评测里不给它（`withoutPreview`，两个 worker 都改了）；扰动见红。

## 没做的，和方案不一样的

- **压缩那一行还是存整份留下的消息**，只是不带图了（方案写的是「只记摘要和从第几条起保留」）：留下的消息里有被省略过的工具输出，按序号引用还原不出来；文字重复一份，量级是每次压缩几百 KB。
- 图的文件没有上限（方案写的每段会话 50 张 / 100MB）：留到做会话摘要那一步一起做。
- 摘要只校验「不是空的」。固定格式、缺节就拒是方案第 3 步。
- 「以供应商报的实际用量为准」没做：`done` 里的用量要先记进会话记录，是第 4 步。
- 盘上不另存原图：进上下文的那一份就是记录里存的那一份。
- 手动保存长期记忆超过 2000 字仍然是截断（`AiServiceImpl.saveMemory`），这一轮只改了草稿确认那条路。
- 没用真模型跑：摘要「明说不思考之后不再是空的」是照代码推的，判据钉的是请求里带了 `instant`、空的进不了历史。
- 网页 / 桌面的代码模式跑的是同一份循环，这些改动跟着进 JAR；桌面应用里没点过。
