# 第二十五轮（2026-10-04）：用户定的三件事 —— 模型判断出不出计划、页面里的提醒、标签页共享登录

## 由来
第二十三轮走主流程照出、需要用户拿主意的三条（`docs/product-plan.md` 第四节 6–8）。用户 2026-10-03 的回答：

- 只说「帮我把下周的工作安排一下」要不要出计划草稿 → **让模型判断**（不再靠关键词猜）；
- 番茄钟、任务提醒到点，页面开着时要不要弹通知 / 响一声 → **做**；
- 没勾「记住登录状态」时新开标签页要重新登录 → **同一个浏览器会话里共享**。

做到一半用户追问（2026-10-04）：「round25 是不是在桌面应用里面也可以增加」—— 加上第四件：**桌面应用的原生通知**。

## 计划（开工时）

1. **模型判断**：消息里有计划词（计划 / 安排 / 任务…）、没有建任务的动词（生成 / 制定 / 添加…）、模型支持工具调用、不是纯聊天时，
   PLAN_EXTRACTOR 照样进图，但调计划工具时 `tool_choice` 用 `auto` 而不是强制，系统提示里多一段「先判断这句是不是要落成日历里的任务」。
   模型没调工具 = 不要，**不再走关键词那条退路去硬抽**（那样等于没交给模型）。有建任务动词的照旧强制。
2. **页面里的提醒**：新接口 `GET /api/reminder/upcoming` 给「接下来 24 小时 + 刚过去 15 分钟」的任务提醒（标题解密好）。
   **不看第三方渠道发没发出去** —— 没配渠道的人（第二十三轮看到的：到点记一条「提醒渠道未启用」就没了）正是最需要它的人。
   登录后每一页都看着：10 分钟取一次清单、30 秒看一次到点没有、切回标签页时各一次、保存任务后马上取一次。
   到点：响一声（WebAudio）+ 系统通知（授权过的话）+ 页面内提示。「提醒过了」按用户记在 localStorage、**先记再提醒**，
   开着几个标签页也只提醒一次。授权只在点击里问（浏览器只在用户手势里肯弹授权框）：点番茄钟「开始」、保存带提醒 / 截止时间的任务。
   番茄钟到点同样走这一套。
3. **共享登录**：`BroadcastChannel('zq-auth')`。没有令牌的标签页启动时先问别的标签页借（400 毫秒没人答就算没有），再去认证；
   落地页借到了就直接进去。退出、改密码（旧令牌作废、换新令牌）都广播，但**只动拿着同一张令牌的标签页** ——
   同一个浏览器里另一个标签页登的是别的账号，不能被这边的退出踢掉。「记住」照旧管跨重启（localStorage）。
4. **桌面应用**：在 WKWebView 里探了一下，`Notification` 存在，但 `requestPermission()` 直接回 `"denied"`，不弹任何东西 ——
   网页通知在桌面版里走不通。外壳加一座桥：页面在桌面版里改 `postMessage` 给 `window.webkit.messageHandlers.zqNotify`，
   外壳用 `UNUserNotificationCenter` 发 macOS 原生通知（窗口在后台、最小化也看得到，Dock 图标跳一下）。
   只认 `notify` / `authorize` 两种消息，标题、正文、标识各有长度上限（页面内容不可信）。声音由页面响，原生通知不带声音，免得响两遍。
   应用在前台时也显示横幅（`willPresent`）；点通知把窗口拉到前面。共享登录桌面版用不上（单窗口），模型判断是服务端的事、重新打包就有。

### 怎么验
真浏览器：一个标签页登录、新开一个不用再登；在一个里退出另一个跟着退；建一条 2 分钟后提醒的任务、等它在页面里弹出来、不重复；
对假模型说「帮我把下周的工作安排一下」看请求里的 `tool_choice` 是 `auto`、出了草稿。新判据先红、扰动见红；全量通过；桌面应用重新打包。

## 结果（2026-10-04）

**模型判断**（`AgentPlanDecision.planMention`、`AiServiceImpl.suggestPlanFromChatIfNeeded` / `PLAN_DECIDE_PROMPT`）：照计划做。
OpenAI 格式 `tool_choice: "auto"`、Anthropic 格式 `{"type":"auto"}`；纯聊天模式、不支持工具调用的模型都不问。
`AiConversationLifecycleIntegrationTest` 的假模型只在请求里**原样**出现「用户刚才的请求：…安排一下」时才调工具 ——
第一版按「包含这句话」判，而判断说明里恰好拿这句当了例子，于是假模型对每一次询问都说「要」，判据一直是绿的。
另外让假模型对退路那条请求回一份计划：不这样的话「模型说不要还硬抽」这个扰动是看不见的（退路抽出来也是空的）。

**页面里的提醒**：`ReminderServiceImpl.upcoming`（最多 200 条；跳过的、已完成任务的不给）、`zhiqu-api.js` 的 `watchReminders` / `dueReminders` / `pageNotify`。
`UpcomingRemindersIntegrationTest` 第一版扰动时「跳过的不给」「完成了不给」两道各删一道都没红 —— 任务一完成，它的提醒同时被跳过，两道条件同时成立、互相替对方挡着。
补了各自单独能照出来的两种：改过提醒时间的未完成任务（旧提醒被跳过、只有前一道管得着）、提醒过之后才做完的任务（提醒不是「跳过」、只有后一道管得着）。
补的时候又踩两个：建任务服务回的对象不带版本号（改任务要先从库里读）；MySQL 的 DATETIME **四舍五入**到秒（不是截掉），带纳秒的时间存进去会多一秒。

**共享登录**：`zhiqu-api.js` 里「同一个浏览器会话里的标签页共享登录」那一段；`auth-share-check.js` 在 node 上建两个「标签页」真的用 BroadcastChannel 互相问。

**桌面应用**：`PageView.swift`（桥、`WeakMessageHandler` —— `userContentController` 强持有处理者，直接挂自己是循环引用）、`ZhiquShell.swift`（通知中心代理）、
打包脚本加 `-framework UserNotifications`。`DesktopPageViewTest` 在真的 WKWebView 里从页面 `postMessage`，看外壳收到的（发通知换成桩，不碰真的通知中心、不弹系统授权框）。

**判据**：`AiConversationLifecycleIntegrationTest`（新的一条：只说安排一下时交给模型判断；改了一条：没出草稿时轨迹不说「已整理」，现在要求模型真的被问过）、原有的 `AgentPlanDecisionWiringTest`（「纯聊天也判断」由它照红）、`PageNotifyAndSharedLoginTest`（node 两份 + 接线两份）、
`UpcomingRemindersIntegrationTest`、`DesktopPageViewTest`（桥）。扰动 20 个全红：模型判断 5 个（不交给模型、一律强制、模型说不要还硬抽、不告诉模型怎么判断、纯聊天也判断）、
页面与桌面 15 个（不先借令牌、退出 / 换令牌不分令牌、翻旧账、重复提醒、先提醒后记账、桌面不走桥、不看着提醒、保存后不刷新、认不出的消息也发、桥没挂上、不截断、
前台不弹、跳过的也给、完成的也给）。最后两个第一遍「红」得不作数 —— 判据本身报错（缺版本号），红的不是那条断言；修好基线再跑才是真红。

**验**：真浏览器（zhiqu_verify、本机假模型）：新开标签页不用再登、一个退出另一个跟着回登录页；2 分钟后的提醒到点在页面里弹「任务提醒：…」、只弹一次
（浏览器面板里网页通知的授权是「拒绝」，走的是提示 + 响一声那条）；「帮我把下周的工作安排一下」→ 请求里 `toolChoice` 是 `auto`、出了一份计划草稿、一个确认框。
全量 910 / 0 / 0 / 0（开着 Docker，集成测试真跑；第二十四轮 903，多的 7 条是这一轮的）；npm 版 237 / 237。桌面应用重新打包（`build/desktop-native`，app 与 dmg）：签名校验通过、外壳链接了 UserNotifications、符号里有桥和通知中心代理、dmg 校验通过；用自带 JRE 冒烟 2.5 秒起来，页面令牌是 `20261004-notify`、发出去的 zhiqu-api.js 带着桥。

**没做的**：真的 macOS 通知中心没在测试里碰（会弹系统授权框）；第一次用时系统会问一次「允许通知吗」。
