# 第一百一十七轮（2026-11-08）：服务器上跑命令

## 由来
用户：「网页版不能操作磁盘，但是可以生成文件到artifact啊，也可以在服务器上跑命令啊」。隔离方式用户定了 bubblewrap（当时以为服务器是 Windows，选的 WSL2 + bubblewrap；服务器其实是 Ubuntu 26.04，直接用）。

这是所有注册用户都能叫起的、跑在放着数据库和主密钥的机器上的命令。**边界错了就是全部用户的数据**，所以默认关（`app.workspace.hosted-shell-enabled=false`），隔离起不来就不给 shell（只生成文件）。

## 计划
1. 服务器用另一份沙箱（`hosted`）：不是「整个根目录只读」，而是**最小环境**：只有 `/usr` 这些系统目录、一个 `/etc` 的小子集、这段对话的临时空间（`/work`）和 `/tmp`。`/home`、`/etc` 的其余部分、`/var`、`/run`（MySQL 的 socket）都不存在。断网（自己的网络命名空间，连本机的 MySQL、Redis、云厂商的元数据服务都不通）；进程看不到外面（自己的 PID 命名空间）；环境变量清空；不能再建用户命名空间（少一大块内核攻击面）；没有提权（`no_new_privs`，`sudo` 用不了）。
2. 限资源（服务器只有 1.9G 内存）：一条命令最多 60 秒；`ulimit` 限进程数、单个文件大小、CPU 时间、打开文件数；优先级最低；`oom_score_adj=1000`：内存不够时先杀它，不杀后端和 MySQL。同时最多 2 条，一个账号 1 条；放不下说清楚。不给后台命令。
3. 白名单的 `run_command` 在服务器上照旧不给：它不在沙箱里。
4. 模型的提示说清边界（断网、60 秒、不能后台）。
5. 判据：Linux 容器里真跑：试读 `/home`、`/etc/passwd`、`/root`、`/proc/1/environ`、数据库目录；连本机端口、外网；写 `/usr`；`sudo`、`unshare`、嵌套 `bwrap`；fork 炸弹、写爆文件、吃满内存、死循环。部署之后在真服务器上再跑一遍。macOS 上这个沙箱不存在，明确跳过，不能假装跑过。

## 结果
边界和取舍写在 [`docs/notes/code-workspace.md`](../notes/code-workspace.md)「服务器上跑命令」那段。计划照做。模型的提示、工具清单跟着改了（说清断网、60 秒、不能后台，没有 `shell_output` / `shell_stop`）。

**真跑才查出来的（每一条读代码都看不出来，都在 Linux 容器里）**
- **根目录默认能写**：写的是 bwrap 自己的内存盘，碰不到服务器，但 `/etc/ld.so.preload` 能盖、也占内存。`--remount-ro /`。
- **`/proc/1/cmdline` 是 bwrap 的全部参数**：服务器上的真路径、账号 id 都露出来了。`--as-pid-1`，命令自己当 1 号进程。
- **普通权限能把 `oom_score_adj` 调回 0**（调回最初的值不要特权）：内存不够时先杀的就不一定是它了。`--remount-ro /proc`。
- **core 的硬上限要是 0**：Ubuntu 的 `core_pattern` 是管道（apport 以 root 在外面跑），里面能把软上限调高就能叫起它。原来判据只看软上限，扰动掉照样绿。

**真的把 Docker 炸了一次**：扰动「进程数不限」时 fork 炸弹没有上限，容器又没给进程数限制，整个 Docker 虚拟机被拖死（6 个多核吃满、守护进程不响应），只能重启 Docker Desktop（问过用户）。用户的容器和数据都还在。两条教训落到了代码和脚本里：**fork 炸弹的判据先确认上限真的设上了才引爆**；扰动用的容器一律带 `--pids-limit`、`--memory`、`--cpus`。这也说明这条限额不是摆设。

**判据**：`test/sandbox-hosted.test.js` 21 条，Linux 容器（bubblewrap 0.8，非 root）全过，macOS 上 16 条显式跳过（不是通过）。试过的逃逸：读 `/home`、`/root`、`/var`、`/run`、真的 `passwd`、`shadow`、别处的密钥文件；连本机端口（有对照）、外网、元数据服务；写 `/usr`、`/etc`、`/bin`、`/proc`；看别的进程、IPC（有对照）、cgroup；`sudo`、`su`、`unshare`、`mount`；软链出去；后端的环境变量。资源：fork 炸弹撞到上限后外面照常、下一条照常；写爆文件停在 64MB；到点连里面的进程一起杀、一个不留。

后端接线（`JsCodeAgent`、`WorkspaceExecutor`、`WorkspaceRegistry`、`HostedShellGate`）：两个开关都开才有；白名单 `run_command` 一直是关的；限时听配置不听模型；后台命令拒绝；闸门真接在执行器上（别的账号、同账号别的对话都轮不到）。

扰动：沙箱 34 处在容器里（红 33；`core 不关` 绿，改判据看硬上限后红；有两处扰动本身写错了，一处没落上、一处是语法错误，重写后红），后端 19 + 复验。绿的逐条查：3 处重复判断互相遮住（生产环境判了两遍，只留一处）、2 处限流没测过接上执行器的效果、4 处 `JsCodeAgent` 的这条路在 macOS 上根本没跑到（补了，这组最要紧：接错了服务器就走普通沙箱，那份的根目录是整个系统）。中途有两条新判据基线就是红的，那一批扰动的「红」作废重跑。

判据：后端全量 1426（1 跳过写明原因）、命令行 441 过 16 跳（服务器沙箱的真判据在 macOS 上显式跳过）、评测工具 102 过 1 跳；Linux 容器里 `sandbox-hosted.test.js` 21/21。

**还没做的、要知道的**
- **还没在真服务器上跑过**。Ubuntu 26.04 的 AppArmor 限制（`apparmor_restrict_unprivileged_userns=1`）要配规则 bubblewrap 才起得来，容器里验不到。部署那一轮要在服务器上把这 21 条再跑一遍，过了才打开开关。
- 内存只靠优先级和 `oom_score_adj`，没有按命令的上限。部署时给后端的 systemd 服务配 `MemoryMax`，内存不够时在它自己的分组里杀，杀到的先是沙箱里的命令。
- 磁盘：单个文件 64MB，一条命令 60 秒能写不少。部署时把临时空间放在单独的小分区或者镜像文件上，写满也只影响这里。
- 内核漏洞挡不住：这是同一台机器上的隔离，不是虚拟机。注册是开放的，真要长期开着，建议以后把命令挪到单独的机器（当时问用户时的第二个选项）。
