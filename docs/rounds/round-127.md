# 第一百二十七轮（2026-11-09）：AI 助手照 Codex 按顺序列出每一步

## 由来
用户 2026-11-09：「还有优化现在ai助手里面的显示，要像codex那样把思考-run command- create -edit- ls 等等命令和结果给按顺序列出来」。

问过之后用户定了：
1. **放进回答里**：每条回答上方一串按时间排的步骤（思考 → 列目录 → 读 → 运行 → 新建 → 修改 …），每步默认一行（动作 + 对象 + 一个结果小结），点开看命令输出 / diff，最后是结论。
   存进库里，刷新、重开都在。右侧「执行轨迹」保留，只放粗粒度的阶段（检索、代码、写回答……）。
2. **代码模式和普通聊天两种一起做**：普通聊天里的检索资料、联网、读任务、读 Wiki、写计划草稿、写 Wiki 草稿也照同样的样子列进回答里。

## 现状（2026-11-09 读代码）
- 代码模式：宿主（`zhiqu-cli/src/host/code-host.js`）只把 `ui.step(text)` 的一行字交给后端（`{type:'step', text}`），后端转成 `agent.step.note`（`phase: call`、400 字截断），
  前端塞进右侧轨迹里那一步的 `notes`，每步最多 40 条，**不存库**，刷新就没了；命令的输出、diff、读了哪几行都没有结构，只有一行说法。
- 命令行 `zhiqu exec --json` 已经有结构化的条目（`item.started` / `item.completed`：`tool_call` 带 `name`、`arguments`、`output`；`agent_message`）—— 就是 Codex 的事件形状，网页没用上。
- 普通聊天：后端的多 agent 执行图（`AgentTraceRecorder`）写 `ai_agent_step`，右侧栏显示每个 agent 的名字和状态；回答里只有正文和「思考摘要」（`reasoningSummary`，2000 字）。
- `ai_message` 没有放步骤的列（V47 是最新的迁移）。

## 计划
1. **一种步骤的形状**（命令行、网页代码模式、普通聊天共用）：`{ id, kind, title, target, summary, status, detail, startedAt, endedAt }`，
   `kind` 一个固定的小集合：`thinking`、`list`、`read`、`search`、`run`、`create`、`edit`、`delete`、`patch`、`web`、`retrieve`、`tasks`、`wiki`、`plan`、`agent`、`other`。
   `detail` 按种类：命令（命令行、退出码、输出的头尾）、改动（diff 的分块，和确认框同一个算法）、读（路径、行号范围）、列目录 / 搜索（命中数、前几条）。每条有上限、说清截断了多少。
2. **代码模式**：宿主把每一次工具调用的开始 / 结束（复用 `exec --json` 的 item：名字、参数、输出）连同思考交给后端；后端照上面的形状归一，流给前端（新事件 `trace.step`），收尾时存进消息。
3. **普通聊天**：执行图里每个 runner 开工 / 收工时，按它干的事给一条步骤（检索了几条资料、联网查了什么、读了几个任务、生成了计划草稿……），同一个事件、同一个存法。
4. **存库**：`V48` 给 `ai_message` 加一列可空的 `steps_json`（只加不改，老数据照样合法）；按条数和字数封顶，超了说清楚省掉了多少；断线从库里接回时步骤也回来。
5. **前端**：回答上方的步骤列表（每步一行：图标 + 动作 + 对象 + 结果小结；运行中的那步在转；点开看输出 / diff；失败的标红），样子进样式表、用设计令牌（不写内联样式、不写死字号），
   浅 / 深两套都对比度够；手机上不横着滚；WebKit 里量（`DesktopWebKitLayoutTest`）。右侧轨迹不再塞逐条叙述。
6. **安全**：命令输出、文件内容是不可信的：一律转义（`esc`），diff 里的 HTML 照样是字；不把密钥类文件的内容放进步骤（和 `read_file` 同一道扩展名门）。
7. **判据**：node 跑发布的前端实现（渲染、转义、截断、展开）；后端归一（宿主的消息 → 步骤）、存取（真库）、普通聊天的每个 runner 都出步骤；宿主发出的条目和执行的工具一一对上；扰动看红。
8. **真浏览器暴力测试**：长命令输出、上百步、超长 diff、连点展开、流式中刷新、断网接回、窄窗口、深色；桌面应用里给用户看（问了再开窗口）。

## 做的时候查出来的
- **一条坏步骤能把整轮停掉**：宿主发一个 `step` 不是对象的 `trace`，Jackson 的 `convertValue` 直接抛出来，后端的读循环 catch 到就停了 —— 判据（假宿主专门发坏消息）先红在这里。改成不是对象就丢。
- **步骤存晚了**：第一版在事务提交、`done` 之前才写，而 run 在事务里就标成完成 —— 页面刷新、判据一看 run 完成就去读，步骤还没进库（普通聊天的判据照出来的；代码模式那条碰巧 300ms 后才读，绿着）。改成在事务里、`completeRun` 之前写，扰动「挪回事务之后 + 等一会儿」红。
- **计划 / 记忆 / Wiki 草稿那几步在 COMMIT 里**：`completeAssistantMessage` 之后才出，所以存库只能在 COMMIT 之后（第一版放在写回答之后就会漏掉它们）。
- **生成到产物也写成了「（草稿）」**：`ArtifactTools` 继承了 `drafts` 这个 Map，原来按「有没有 drafts」判，产物模式写的真文件也标草稿。改成看 `artifact`。
- **补丁的加减行数按截过的分块数**：改动超过 400 行时数出来的是错的。改成按整份算（`stat`）。
- **第一百二十六轮漏跑了后端全量就提交**：`zhiqu update` 的 npm 子进程超时参数叫 `timeoutMs`，`IdempotencyLockSpanTest` 把命令行里所有 `timeoutMs` 当成请求超时、算出 5 分钟 × 3 轮，结果留存时长不够 —— 红着提交了。改名 `killAfterMs`（它不是对服务器的请求）。
- 联网那一步原来拿不到搜的是什么（query 在 `WebResearchService` 里拼完就丢了）：加 `researchTraced` 一并交回。
- 任务标题在库里是加密的：「读任务」那一步只说条数，不往明文的步骤里抄标题。

## 结果
- 一种形状三处共用：命令行 `zhiqu-cli/src/steps.js`、后端 `TraceSteps`、前端 `traceStepsHtml`。种类 19 个（思考、列出、读、搜、运行、新建、修改、补丁、删除、联网、检索、任务、知识库、计划、记忆、核对、子 agent、清单、其它），每个有图标（新加 `terminal`、`file-plus`、`brain`，Lucide）。
- 代码模式：宿主每次工具调用开始 / 结束各发一条 `trace`（命令的输出头 20 行 + 尾 40 行、退出码、diff 分块、行号、命中、清单），思考字数和时长；后端照形状收、按上限截（输出 16000 字、diff 400 行、20 个文件、30 项、一轮 200 步），SSE `trace.step` 实时给页面。
- 普通聊天：检索资料（几份、几段、换没换说法，点开是资料标题）、联网（搜了什么 / 读了哪几个网址、几个结果、几个打不开）、读任务（只说条数）、知识库读写、计划草稿（几个任务 / 例行计划，等确认）、记忆草稿、核对引用、思考几秒。
- 存库：V48 `ai_message.steps_json`（可空，只加）；实体上 `select = false`、只在 `saveSteps` 里写（整行 `updateById` 碰不到、历史查询不拉这一大列）；事务里、`completeRun` 之前写；失败也写（还在跑的收成「没做完」）；`done` 带一份；消息列表一次批量查回。
- 页面：回答上方一步一行（图标、动作、对象、结果小结、用时），有细节的点开（命令输出带 `$ 命令`、省掉几行写在头尾中间、退出码；diff 照确认框的样子；列表；清单划掉做完的）；跑着的那一步转圈（减少动效时不转）；出错的标红；上百步默认列 60 步、剩下的折成一个按钮；展开状态按 requestId 记（流式补丁、收尾重拉列表之后都还在）；`trace.step` 只重画这一条回答。右侧执行轨迹照旧。

## 自己 review（用户：「做完后自己review，然后commit+部署」）
找了一个没看过这段代码的 agent 读整份 diff（只读），2 条 P2、8 条 P3，没有 P0 / P1；都修了，判据见红（11 个扰动）：
