# 第一百三十二轮（2026-11-12）：桌面应用自己更新、生成中还能发消息、RAG 卡在 BUILDING

## 由来

三件事挤在同一天，都来自用户在线上试的时候撞到：

- 「能不能做到桌面应用版里面的自己获取更新，然后提示是否要更新重启应用，不然每次都要打包下载，很麻烦。就像 codex 和 dsh 那样，左下角有一个更新下载的提示，点击后自动更新」
- 「为什么一直显示进度 0%，然后一直在 building」
- 「修复 2，然后增加在模型处理的时候可以发送消息（立即 / 排队）」「还有增加轮次，20 轮太少了」

## 要做的

**桌面自更新。** 服务器不用改：第八十二轮的 `/api/desktop/downloads` 本来就返回每个平台最新包的
`version / size / sha256 / url`。外壳只做四件事：问一句、比版本、下载并核对、换掉自己。

- 启动问一次，之后每 6 小时一次，切回前台一小时最多一次。
- 版本按数字逐段比（`1.0.10 > 1.0.9`）；按字符串比会得出相反结论，那样永远收不到更新。
- 下载完算 sha256，对不上就删掉、不装。
- 替换交给一个一次性脚本：等主进程真退出 → `ditto` 到旁边 → 成功了才换 → 重新打开 → 清临时目录。
  正在跑的 bundle 不能边跑边删；先拷后换是为了拷到一半失败时原来那份还在。
- 左下角一颗胶囊：「有新版本 1.1.0」→「正在下载 42%」→「重启完成更新」。重启这一步留给用户点，
  不替他决定什么时候断。右边的 × 只压这一个版本。

**生成中还能发消息。** 原来 `sendAiMessage` 开头是 `if (state.aiSending) return;` —— 生成中发出的字
被静默吃掉，用户以为发出去了。改成进队列：输入框上方一条一行「排队 1：…」，带「立即」和「×」，
这一轮结束（`finally`）自动发队首那条。发送键在生成中不再 `disabled`（那样根本没机会排队），
只换成转圈的样式。

**RAG 一直 BUILDING。** 线上第 5 代卡在 `BUILDING 3/4`，作业 28 重试到第 5 次，`last_error` 是
`Error while extracting response for type [java.util.Map<?, ?>] and content type [application/octet-stream]`。
看着像旁路坏了，其实旁路是好的（`/v1/meta`、`health/ready` 都正常）。根因是后端只有一份
`RestClient`，读超时 `app.rag.read-timeout-ms: 1800`（1.8 秒）—— 那是**查询**的预算。建索引一批
8 个父块要现算 24 个向量，在服务器上实测 **4.72 秒**，每批都在读到响应前被掐断，Spring 把断掉的
响应当成 `octet-stream`。前面三个单元只有 2~7 块，碰运气能过；卡住的那个是 704 块、1.5MB 的
笔记本资料，要发 88 批，一批都过不去 → RETRY 到 DEAD → 代次永远 BUILDING。

**轮数。** `CodeLoopBudget.EXPLICIT` 20 → 40（时间仍 240 秒）：一轮读一个文件时先撞到的是轮数，
不是时间；把轮数放开，让时间当唯一的闸门，不会把整条流撑过 300 秒。

## 怎么验

- `DesktopUpdaterTest`：编一个 Swift 检查程序，钉住版本比较的六种情况、清单解析（没有 macos、
  不是 JSON 都当没有）、sha256 对标准值、替换脚本必须等进程退出且先拷后换、打包脚本编进了两个
  新文件。扰动（版本比较改成按字符串）见过红。另外把替换脚本单独跑了一遍（`open` 换成 echo），
  确认它真的把 target 换成了新的、没留 `.old`、临时目录也清了。
- `RagClientTimeoutTest`：同一个慢旁路（2.5 秒才回），建索引要过得去、查询要按查询预算掐断。
  扰动（把建索引那个 client 换回查询的超时）**复现了线上那句一模一样的 octet-stream**。
- `AiComposerTest` 跟着新行为改了三处断言，并新增「生成中不许禁用发送键」。
- `CodeLoopBudgetTest`、`StaticAssetCacheTokenTest` 通过。

## 结果

- 服务器上第 5 代从 `BUILDING 3/4` 跑到 `READY 4/4`，作业 28 `COMPLETED`。管理后台的进度改成
  看 BUILDING 的那个代次（原来算的是已建好的活动代次 0/0，所以永远 0%，而下面明明写着 BUILDING 3/4）。
- 本机装上 1.0.0（带自更新的那份），服务器上换成新打的 1.1.0（sha256 `c22e6dfd…`），
  打开就是「有新版本 1.1.0」。
- 胶囊第一版用 `bottom: -16` 压住了侧栏底部的用户名（用户截图指出），改成 `-72` 让开那块。

## 遗留

- 打包最后一步 `hdiutil create` 报「设备上无剩余空间」，`/System/Volumes/Data` 其实还剩 169G，
  多半是 APFS 快照的问题；`.app` 是好的，不影响安装。
- 管理后台的「启用」要用户自己点一下，索引建好不会自动生效（第一百二十四轮只做了「一个都没有时往前推」）。
- 「立即」当时是 abort 当前这条流 —— 用户看着出来的半截回答当场没了。下一轮改掉。
