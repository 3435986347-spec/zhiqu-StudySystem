# 第十八轮（2026-09-28）：暴力测试 —— 命令行的数据量极端

## 由来
第十七轮在网页上造了一个「用了两年」的账号，照出了好几处「取回全部」「每条都查一遍全表」。命令行这一侧还没这么量过：
一个用了很久的工作区里有几百段会话、有一段对话记了几万条、项目本身有几万个文件、接了好几个 MCP 服务器、几百个工具。

## 计划（开工时）
先造出来、真跑、量时间和内存，再修；判据先红、扰动见红。

### 1 会话
- `.zhiqu/sessions/` 里几百段：启动、`/resume` 列表要多久。
- 一段几万条记录（几十 MB）的会话：`/resume` 接上要多久、内存多少；回放聊天记录会不会把终端刷屏几分钟。

### 2 工作区
- 几万个文件、很深的目录：`list_files`、`search` 要多久，截断有没有说出来；`node_modules` 这类有没有被跳过。

### 3 工具
- 几个 MCP 服务器、几百个工具：每一轮发给模型的工具定义有多大（占多少窗口），启动要多久。

### 修
照出来的都修，数量不设上限。

## 结果

造的：500 段会话（每段 20 条）、一段 4 万条的会话（16MB，带工具调用和大段工具输出）、5 万个文件（500 个目录 × 100）、
node_modules 里 3000 个文件、一个 300 个工具的假 MCP 服务器。

| 量的东西 | 改之前 | 改之后 |
|---|---|---|
| 列会话 / 最近一段（500 段） | 1ms | 没动 |
| 接上 4 万条的会话（load） | 66ms、堆 +51MB | 没动（真实的长会话压缩过，load 只拿最后一次压缩之后的） |
| `/resume` 回放 | 往终端打 30002 行、2.7MB | 63 行，说「前面还有 N 轮没显示、完整记录在哪」 |
| 搜索（5 万个文件，要找的在最后一个目录） | 只看了前 3000 个文件、「0 处（已截断）」 | 1.1 秒找到 |
| 配了 MCP 的 `zhiqu -p` 退出 | 15056ms | 76ms |
| 300 个 MCP 工具时每一轮发给模型的工具定义 | 308 个、15 万字 | 9 个、3.6K 字（`find_mcp_tool` 按需找） |

### 查出来的
- **每次多等 15 秒**：MCP 连接超时的定时器连上之后没清。它不报错、只是慢，所以一直没人发现 —— 连测试也跟着多等（MCP 的测试文件 10 秒 → 6.5 秒）。
- **工具定义占掉一大半窗口**：MCP 工具的定义每一轮全发，300 个就是 15 万字；64K 窗口的模型还没开始干活地方就不够了。
- `/resume` 回放整段；搜索的文件数上限太低（而且每个文件新分配 1MB 缓冲 —— 5 万个文件就是 50GB 的分配）。
- 量了之后没问题的：列会话、`list_files`（到 500 条截断并说出来）、node_modules / build 这类目录本来就跳过、接上大会话。

### 扰动
9 处，全红（其中「定时器不清」那处这条判据等了 16 秒才红 —— 就是那 15 秒）。
