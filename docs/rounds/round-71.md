# 第七十一轮（2026-10-18）：换编辑器第 1 步 —— 阅读这头先对、保存不再替用户改字

## 由来
第七十轮验证 CodeMirror 6 的实时预览后建议分三步迁；用户在桌面应用里试了验证版：「感觉整体没有明显差异，新编辑器在点击光标定位会快一点，其余都行」（中文输入法等没问题）。
第 1 步是阅读那头：编辑器保住了原文，阅读时还是会把嵌套列表压平；后端存的时候还会改字。

## 第七十轮留下的两件 + 这轮一开始查出来的
1. **阅读模式不认缩进的嵌套列表**：`  - 嵌套一` 显示成文字「- 嵌套一」（`renderMarkdown`）。AI 助手的回答也走它。
2. **后端存的时候改字**：用户保存一页也要过 `MarkdownCanonicalizer.clean()`，而它是给 AI 写的内容准备的 ——
   去掉首尾空白（Obsidian 的文件结尾都有换行）、正文以 ```` ``` ```` 开头时剥掉开头的代码围栏（一页以代码块开头，代码块就坏了）、
   删掉只有 `#` 的行、**删掉同时含「已将 / 已经 / 已存入 / 已写入」和「知识库 / Wiki / 知识树」的整行**（用户写「我已经把资料整理进知识库了」，保存后这一行就没了）。
   读一页（`pageRow`）回给页面的也是清洗过的。

## 计划
1. 后端：用户自己保存的正文原样存（只把 CRLF 统一成 LF），读一页原样回；AI 写的（待合入变更、修订）照旧清洗；
   冲突检测的页状态哈希和 RAG 的规范全文照旧都用 `clean(解密)`，两边同一个口径，不用重算存量。导出 ZIP 写原文、以换行结尾。判据先见红。
2. 前端：`renderMarkdown` 认嵌套列表（2 / 4 空格、有序无序混着、任务项、列表项里的续行）；旧编辑器（第 3 步之前还是默认）的 `htmlToMarkdown` 把嵌套列表写回缩进，不能比现在更坏。
   用 markdown-check 的真跑判据，先见红。
3. 真浏览器：第七十轮的 14 页语料两种编辑器各再走一遍「不改保存」，量逐字节一样的页数；嵌套列表阅读的样子截图。
4. 收口：全量（开 Docker）、本轮记录、README 和 CLAUDE.md 各一行、桌面应用重新打包、提交（不推）。

## 结果

**后端：用户保存的正文原样存、原样读回**（`KnowledgeServiceImpl`）
- `savePage` 只把 CRLF / CR 统一成 LF；空正文照旧拒绝（原来的 `required()` 会 trim，结尾的换行也是它去掉的 —— 判据第一遍改完还红，就红在这里）。
  `pageRow`（读一页、保存回包）原样回；摘要去掉首尾空白。旧的 Markdown 导出（`/export/markdown`，页面上已经不用）写原文、以换行结尾；页面上用的 ZIP 导出本来就是原文。
- AI 那头不动：修订、待合入变更照旧清洗；页状态哈希、给模型的快照、RAG 的规范全文照旧是 `clean(解密)`，两边同一个口径，存量不用重算。
- 真 HTTP 里：13 页语料 POST 进去，回包和发出去的逐字节一样 13/13（第七十轮 12 页里 11 页少了结尾换行）；新编辑器点进编辑、真存进库再读回，结尾没换行的、嵌套的两页都一样（版本 0 → 1）。

**前端：阅读模式认嵌套列表**（`renderMarkdown`，AI 助手的回答也走它）
- 列表是一摞：每层记缩进和种类（无序 / 有序 / 任务）。比上一层多缩进两格以上是嵌套（2 / 4 空格、Tab 算 4 格）；缩进退到父项那一档才收掉更深的层，缩进不齐的同一层不另起。
- 任务项照旧画成 `.zq-task-row`；在列表项下面的就放在那一项里，它自己下面的子项放进 `.zq-task-children`（缩到勾选项文字的位置）。
- 列表项里缩进的续行接在这一项里（`<br>`），空行之后缩进的段落是这一项里的 `<p>`；编号不从 1 开始的写 `start`（原来「1. 甲 / 空行 / 2. 乙」两段都显示成 1.）。
- 不变的：顶层列表之间隔空行照旧是两段、换种类另起、不缩进的下一行和代码块照旧收掉列表。

**旧编辑器（第 3 步之前还是默认）的 `htmlToMarkdown`**：嵌套写回缩进、编号照原样（原来一律「1.」）；勾选项一行一个、和普通列表项挨着也不插空行（原来每条后面都空一行）；
列表项文字后面的段落 / 勾选项另起一行（原来粘在文字后面）。点一下嵌套在列表项下面的勾选框再保存，写回去只有那一项变成 `[x]`，结构保住。
