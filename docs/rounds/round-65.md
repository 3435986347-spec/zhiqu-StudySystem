# 第六十五轮（2026-10-14）：macOS ZIP 兼容、Wiki 正文宽度与弹窗稳定性

## 用户问题

- 桌面 `risk.zip` 在 Wiki 中预览时提示「ZIP 无法读取或已损坏」。
- 询问 Markdown 与图片之外的文件是否可以放进 Wiki。
- Wiki 内容区很宽，正文仍提前换行；弹窗打开时背景页面轻微移动。
- AI 助手输入框适当下移，减少底部留白。

## 计划

- 只检查真实压缩包的格式与完整性，诊断信息不输出笔记正文，不修改原 ZIP，不写入真实 Wiki。
- 构造 macOS ZIP 格式的合成回归样本，先见 assertion red，再修复读取方式；保留路径、条目、解压大小与 CRC 校验。
- 用实际压缩包执行只读解码验证，并检查合成 ZIP 的浏览器预览；确认普通附件仍保留字节和链接。
- Wiki 阅读与编辑正文随可用区域宽度排版；检查宽屏、窄屏和长文本，保留合理内边距。
- 检查弹窗滚动锁定与焦点管理，打开、关闭和连续切换时背景位置稳定。
- 调整 AI 助手内容区域底部空间，在桌面和窄屏检查输入框位置。
- 完成相关离线测试、代码审查、round 记录、提交和推送。

## 实现

- `risk.zip` 的文件 CRC 全部有效；原因是 macOS 压缩包含有 STORED 条目和 data descriptor，JDK 的 `ZipInputStream` 不支持该组合，被旧逻辑误报为损坏。改用中央目录读取 `ZipFile`；仅暂存有大小限制的原压缩包，条目始终在内存处理，不按条目路径写磁盘，关闭后删除临时包。
- 保留所有条目的路径、重复路径、实际解压大小和数量限制，包括跳过的元数据；显式校验实际长度与 CRC。先排除 `.obsidian`、`__MACOSX` 等设置或系统文件，再识别知识库根目录。JSON、PDF、Office 等普通附件仍按原字节保存并关联；正文抽取沿用上传文件解析来源入口。
- Wiki 阅读和编辑正文取消 `42em` 固定上限，使用内容区可用宽度；图片不越界，长网址换行，代码和表格在自己的容器内滚动。
- 弹窗打开时保留滚动条槽位，兼容代码测量 `body.clientWidth` 的实际变化；聚焦不带动背景，嵌套弹窗在最后一层关闭后才解除滚动锁。浏览器实测发现 `documentElement.clientWidth` 在保留槽位时仍会改变，已补上这个差异的判据，避免重复补偿。
- AI 对话页取消普通页面额外的页脚留白，输入区保留约 22px 底边距及设备安全区；多行输入不改变底部位置。全站缓存版本同步为 `20261014-wiki-zip-compat-width`，首页 AI/Wiki 浅深色截图以合成数据更新。
