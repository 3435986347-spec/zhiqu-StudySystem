# 第一百四十五轮（2026-11-17）：应用的会话在命令行里接着做 —— 第 1 步：桌面代码模式写会话记录

方案 [`docs/app-resume-plan.md`](../app-resume-plan.md) 的第 1 步。用户 2026-11-17 定了三件事：
没有文件夹的会话也要能 `/resume`（标明「只有文字」，第 3 步）；两边都能开着同一段会话，一次只有一边在跑一轮（第 2 步）；记录 id 用 `app-<Notebook 号>`。

## 由来

用户：「在命令行里发起的会话在应用里能看到，但是在应用里发起的会话，命令行里却看不到。同时最新增加的 memory 功能应用版是否能用得上？」

两件事是同一个缺口。桌面应用的本机代码助手跑的就是命令行那一份循环（`code-host.js` → `runTurn`），只是起它时 `store: null`：
没有会话记录，所以命令行的 `/resume` 看不见；记忆方案第 5、6 步（跨会话、项目笔记）、第 3 步的大输出存盘、第 4 步的用量记录都挂在「有会话记录」上，应用里一样都没有；
第 2 步的状态卡整个文件夹只有一张（`.zhiqu/state.json`），同一个文件夹开两段对话会串。
另外每一轮只拿到页面拍扁的问答（`historyBlock`），上一轮读过什么、改过什么都没了。

## 做了什么

- **页面**（`sendDesktopTurn`）：交给外壳的一轮多带 `sessionId: 'app-<Notebook 号>'`（「默认对话」是 `app-default`）和每条历史消息的号。
- **外壳**（`LocalAgent.swift`）：照传。会话 id 只认 `[A-Za-z0-9_-]{1,64}`（拼进文件名），消息号只认正整数，认不出的当没给。
  id 不限于 `app-` 开头：第 2 步在应用里接着说命令行来的会话时用的是命令行的 id，到时候不用再改外壳、不用再打包。
- **宿主**（`code-host.js` 的 `openAppSession`）：桌面版、给了合规的 id，就在项目的 `.zhiqu/sessions/` 里开一份和命令行一模一样的记录（`SessionStore.adopt`：用给定的 id，索引里没有就补一条，标 `via: 'app'`）。
  - 记录在：前面的对话用记录里的消息（带工具调用）。
  - 记录里没有、对话里有的几轮（在普通聊天、网页上接着说的）拍扁成「只有文字，供参考」追加一次。**对账**：记录里记一行 `sync`（这一轮带来的最大消息号），比它新的才看；
    比它新、但这份记录里人说过的（`said`，`runTurn` / `recordExchange` 每一句记一行原话）按顺序对掉，连同后面的回答。同一句「继续」说两遍也对得上；对账点之前说过的话不参与。
  - 记录不在：照原来拍扁整段问答起头，也写进记录（命令行 `/resume` 回去时一样有）。
  - 旧版共用的 `.zhiqu/state.json`：上一轮没做完的话，状态卡作为一条说明接进这段一次，然后删掉。从此状态卡按会话分开（`sessions/<id>.state.json`）。
  - `/review` 的结论也记进会话（和命令行的 `/review` 一样）。
  - 存档照旧关着：这一轮的问答由页面存进对话，宿主再存一份就重了。
- 于是这些在应用里自动有了（不用另写）：开工时知道这个项目最近几段会话、`search_sessions` / `read_session`、项目笔记和项目地图、大输出存盘可取回、用量进记录、状态卡跟着会话走。
- **后端**（`HarnessSessionService.open`）：命令行往 `app-<号>` 存档时，这个号是这个用户自己的、还在的对话，就绑到它上面，不另建「命令行 · …」；
  别人的号、删掉的号照旧新建。并发撞上时，原来会删掉「多建的那个对话」—— 绑上的是用户自己原来的对话，不能删。
- **命令行这边这一步没改**：`app-*` 的记录就在 `.zhiqu/sessions/` 和索引里，`/resume`、`--resume`、`exec resume` 本来就认。

## 顺带修的

- `slash-check.js` 有两条在 master 上一直红着（「能发的时候：交给本机代码助手……」「⌘/Ctrl + 回车……」）：桩里外壳的 `resume` 动作回 `{}`，
  第一百三十三轮起页面靠它拿结果，上一轮永远收不了尾，「正在回答」漏到下一条检查里。是桩落后于实现（判据的纪律第 9 条），桩改成回终态。
  第一百四十二轮的「后端 0 失败」说法和这个对不上，原因没查（那一轮可能没在这台机器上跑，或者 node 的位置不同）。

## 判据

- `zhiqu-cli/test/desktop-host.test.js` 加 7 条（「应用会话：……」）：第二轮看得见第一轮的工具结果、记录和索引在、命令行读得回来（对照：不给 id 看不见）；
  别处说的几轮只补一次、记录里有的不重复、前情只在第一次带；同一句话说两遍按顺序对账、对账点之前的话不参与；旧状态卡接一次就删；
  有别的会话时开工就知道、给 `search_sessions`、项目笔记进来（对照：不给 id 都没有）；`/review` 记进会话；坏 id、临时 id、不是桌面版不建记录。
- `slash-check.js` 加 1 条：交给外壳的那一轮带会话 id 和消息号、默认对话是 `app-default`。
- Swift 检查程序（`DesktopLocalAgentTest`）加 5 个断言：id、消息号照传给宿主，认不出的不传。
- `HarnessSessionBindTest`（新，单元）4 条：认得的 id、绑到自己的对话、别人的号新建、并发撞上不删用户的对话（对照：命令行来的 id 照删）。
- `HarnessUsageIntegrationTest` 加 1 条真库的：存档落在原来那个对话里、别人的号不绑。**这台机器没有 Docker（不让装），这条没跑过、也没见过红。**
- 扰动 34 处全部见红：宿主 21、页面 3、后端 5、外壳 4，外加 1 处第一遍没红 —— 宿主自己的 id 规则被 `SessionStore.file()` 的同一条规则替它挡了，
  补了只有它照得出的样本（直接问 `appSessionId`）后见红。扰动时顺手去掉了一个照不到、也不必要的条件（旧状态卡「这段会话已经有状态卡就不接」）。
- 真进程端到端（`/tmp` 里的脚本，假网关）：真的宿主进程按外壳的起法跑两轮 → 真的命令行进程 `zhiqu exec resume app-12` 接着说：
  发给模型的消息里有应用第一轮读到的文件内容、第二轮的回答，同一句话只出现一次；存档发往 `/api/harness/sessions/app-12/messages`；
  再回到宿主跑一轮，命令行那一句只出现一次、命令行的回答在。

## 没做的，和方案不一样的

- **没有重新打包桌面应用，也没在桌面应用里用鼠标点过**：外壳和宿主都在安装包里，不重打用户拿不到；打包、开应用要碰真账号的数据，先问用户。
  方案里写的「重打桌面应用，真鼠标点两轮」没做。也没有真浏览器的暴力测试：这一步的改动只在桌面应用里生效，网页上没有本机代码助手。
- 旧外壳 + 新页面：外壳不认 `sessionId`，宿主照旧不记 —— 和以前一样，不会更坏。
- `app-default`（默认对话）后端不绑：默认对话不是 Notebook，命令行往它存档还是会新建「命令行 · …」。留给第 2 步。
- 旧状态卡接进来时，清单不跟着回来（原来的 `inheritedCard` 会把清单带回 `ctx.todos`），只有状态卡的文字。
- 同一个文件夹里两段对话同时跑、命令行和应用同时跑同一段 —— 第 2 步的锁还没做。现在外壳一次只跑一轮，所以应用这边自己不会撞。
- 没用真模型跑。

## 结果

- 命令行 `npm test`：624 条，605 过 / 19 跳过 / 0 失败。
- 后端 `mvn -o clean test -Dzhiqu.skipDockerTests=true`：1519 条，0 失败，267 跳过（全是要 Docker 的集成测试，这台机器没有 Docker），BUILD SUCCESS。
  **跳过的不算通过**：新加的那条真库判据和其余集成测试要在有 Docker 的机器上补跑。
