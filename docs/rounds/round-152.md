# 第一百五十二轮（2026-11-17）：干活中途补充第 3 步 —— 网页代码模式

## 由来

[`docs/steer-plan.md`](../steer-plan.md) 第 3 步。命令行（第一百五十、一百五十一轮）能中途补充了，网页这边还是第一百三十三轮的样子：
「立即」只在最终回答动笔之前并进去；代码模式的最终回答就是代码 agent 自己的结论、不再调模型，所以补的话**一律没用上**，
只弹一句「没赶上这一轮，不会自动重发」。用户定的：网页上生成中按发送，默认就补给这一轮。

## 要做的

- **宿主（`code-host.js`）**：
  - 桥认 `say`，回 `say_ack { accepted }`。收到 run 之后、收件箱挂上之前到的 say 先收着（和 run 落在同一块数据里时，readline 会在 run 的回调跑之前把下一行也交出来）。
  - `runHosted` 最先建这一轮的 `Inbox`。run 里带来的 `steer` 是循环起来之前就补了的，先放进去。
  - 模型读到时记一步 `steer`（「你补充」，原话在 target），再发一行 `steered`（原话）。
  - 收尾没读到的放进 `result.leftover`；所有提前返回的路（busy、桌面令牌不对、/review 不跑循环）也一样交回。
- **`steps.js` / `TraceSteps`**：多一种 `steer`。
- **`SteerPort`（新）**：后端往宿主递话的口子。宿主起来之前收着；`start` 在同一把锁里把收着的随 run 交出去、挂上真正去说的函数；之后 `say` 直接说给宿主（锁外等回音）；`finish` 之后一律不收；`unconsumed` 交回谁都没收走的。
- **`JsCodeAgent`**：
  - 带 `SteerPort` 的新重载。
  - `say` → 宿主 → `say_ack` 交接（等 5 秒）。
  - `steered` 转成 `phase=steered` 的叙述；收尾时把宿主的 leftover 放回口子。
- **`AiServiceImpl.StreamState.inject` 三段**：最终回答已动笔 → 下一轮；代码 agent 在跑 → 交给口子；否则收着、最终回答时并进去。
  - 代码 agent 前后开、关口子，谁都没收走的放回来（排前面）。
  - 最终回答那一步：调模型的路发 `message.steer.delivered`；代码结论那条路发 `message.steer.returned`（原来那句「不会自动重发」删了，话不再丢）。
- **`ChatRunHub.LiveRun.inject`**：锁里只取 turn、锁外交给它。代码模式下要等宿主回音，读宿主输出的线程同时要 `emit`（同一把锁）。
- **页面**：
  - 生成中按发送 → `steerSend`：排队条一行「补充 · 发送中 / 待送达」，没有按钮（撤不回来）。
  - 服务端 `current` = 收下了，等 `steer.delivered` 再拿掉；`next`、出错、`steer.returned` → 变回排队、排最前面。
  - 这一轮结束还写着「待送达」的变回排队，照顺序发（用户定的：没赶上就接着发）。
  - 排队条的按钮改叫「立即补充」；回答里多一种步骤「你补充」（图标 `message-square`，原话不用等宽字）；发送键的读屏说明改成「生成中（发送 = 补充给这一轮）」。
  - 换缓存令牌 `20261117-r152`。

## 本机后端 + 真浏览器里撞到的（判据都是绿的）

本机后端（`zhiqu_verify` 库、新注册的 `r152steer`、假的 OpenAI 兼容模型：代码 agent 第一次调用停 30 秒、看到补充就把原话说出来）+ Chrome（playwright-cli）。

**同一句话进了这一轮，又成了下一轮。** 假模型的记录里，第 9 次请求已经带着「测试用 pytest」，第 10 次请求又把它当成新的一轮发了出去。

- **原因**：后端读宿主输出的就是替宿主调模型、跑命令的那个线程，模型调用一停几十秒，宿主早就回的 `say_ack` 没人读。5 秒等不到就当没收下（`next`），页面排进队列，这一轮结束又发一遍。真实场景里模型调用、跑命令几乎占满全程，所以几乎每次都会撞上。
- **判据为什么没照出来**：`JsCodeAgentSteerTest` 让假模型先睡 300 毫秒再回，回音恰好在那之后被读到。
- **改法**：读宿主输出单独一个线程（`code-host-reader`），`say_ack` 一到就交接，别的行照原来的顺序交给主循环。
- **判据**：改成真实的样子 —— 补充有结果之前模型这次调用不回 —— 并钉「模型调用还没回就该知道收没收下」（扰动「回音交回主循环」见红）。
  第一版只看最后 `accepted == [true]`，扰动没红：旧做法下回音只是晚到，最后照样是 true。

**读线程第一版把整个循环卡死了。** 输入流放在 `try-with-resources` 里：主线程走出去时要关它，读线程正卡在 `readLine` 里攥着同一把锁，宿主又要到后面的 `finally` 才被杀，两边互等。`JsCodeAgentTest.门在后端` 跑了 12 分钟不结束（线程栈看到的）。改成输入流归读线程，读到结束自己关。

其余走通的：

- 补的话进了正在跑的那一轮：回答里「读取」之后一步「你补充」，最终回答照着补充说。
- 排队条在模型那 30 秒里一直是「补充 · 待送达」，读到后收掉。
- 补完、送达之前**刷新页面**：「待送达」还在，接回来后被收掉、没有重发，「你补充」那一步刷新后还在（存进了库）。
- 上一轮刚好结束时发的，是新的一轮（不是补充）。
- 页面上两处小毛病，看截图改的：发送键的读屏说明还写着「回车 = 排队」、补充的原话用了等宽字。

## 怎么验

## 结果

网页代码模式能中途补充了：跑完当前这一步（模型说完这一次 / 命令跑完）就读到，回答里看得见在哪一步读到的。普通聊天照旧在最终回答之前并进去（Wiki 工具 agent 的轮间读取是第 5 步）。
要部署到服务器才生效（页面、后端、JAR 里带的命令行宿主都在这一份里）。
