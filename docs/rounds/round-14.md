# 第十四轮（2026-09-28）：暴力测试 —— 网页上没耐心的人（真浏览器）

## 由来
用户 2026-09-28：「同时暴力的测试这个东西比如不同输入，不停刷新，测试没有耐心的极端情况」。第十三轮在服务器一侧做了
「同一个动作并发 20 次」「AI 回答时狂刷新」，命令行做了 Ctrl+C。这一轮到**网页本身**：人在浏览器里连点、连按回车、
来回切页面、网慢的时候等不及。

收口第十三轮时顺手扫了一眼 `assets/zhiqu-api.js`：62 处写操作里，只有「套用参考计划」（第八轮）和发消息按钮在请求回来之前
挡住了第二次点击。新建例行计划、新建 Wiki 页、加 Raw Source、新建 Notebook、加模型、提交参考计划、注册……双击的话
很可能各建两份 —— 服务器没法替它去重（两次都是合法的新建）。

## 计划（开工时）

### T2b-1 连点：每个会「新建」的按钮
- 在真浏览器里对每个新建类按钮双击 / 连按回车，数服务器上建出了几份。先实测，别凭读代码下结论。
- 修法要是**一处**：一个「请求没回来之前这个动作不再响应」的机制，所有写操作走它；而不是每个按钮各自 `disabled = true`
  （62 处各写一遍，漏一处没人知道）。
- 判据：node 上直接跑发布的那份实现（和 `request-check.js` 一样），再加一条扫源码的：新建类的 `api.post` 都经过它
  （去注释、给扫到的数量设下限，免得扫空了也绿）。

### T2b-2 来回切：请求回来时页面已经换了
- AI 助手里快速切 Notebook、Wiki 里快速切页：前一个的响应晚到，会不会画进后一个里（A 的消息显示在 B 下面、在 B 的编辑框里保存了 A 的正文）。
  拿网络限速 / 在响应上加延迟来复现。
- 判据：晚到的旧响应不画、不覆盖。

### T2b-3 网慢 / 断网时的按钮
- 请求超时或失败之后，按钮要能再点（不能永远卡在「保存中」）；成功之后弹窗关掉，失败之后弹窗留着、填的字还在。

### 顺带
- 每次全量测试跑完，surefire 都要等 30 秒才强杀测试 JVM（「The exit has elapsed 30 seconds after System.exit(0)」，
  第九轮以来的每一份全量日志里都有）—— 有个非守护线程不退。查出是哪个，全量少等 30 秒。

### 暴力测试（每轮都做）
- 以上三块本身就是。另加：一个页面上 1 秒内点 50 下各种按钮，页面不报错（控制台没有未处理的异常）、服务器没有运行问题。

## 结果

### T2b-1 连点：真浏览器里双击「创建例行计划」
- **第一下成功、第二下「服务器出错了」**。查下来是个通用的 bug，不只是例行计划：`@DeadlockRetry` 标在 15 个服务方法上而且互相调用
  （新建 → 成就检查，两个都带）。两个请求同时解锁同一个成就就死锁，MySQL 回滚的是整个事务，里层的重试在死掉的事务里把成就检查再跑一遍，
  外层提交时 `UnexpectedRollbackException`。现在只在最外层的事务边界上重试。并发暴力测试加了「同时新建 20 个例行计划、20 个任务」
  （各建出 20 个、成就积分只加一次），修之前红、连跑 5 次都绿。
- **服务器修好之后，双击还是建两个**（两个请求都是合法的新建，服务器没法去重）→ 网页的 `request()`：同一个写请求没回来前不重发，
  两次点击拿同一个结果。真浏览器里看网络记录：双击只发一个 POST、两边各重载一次列表。
- 回来之后多点的那一下还是新的一次（本机几毫秒就回来了）→ 页面上常驻的新建表单建好就清空（弹窗一建就关，本来点不到）。
  改完：双击 + 补一下 = 一个计划、一句「请输入标题」。Wiki「新建知识页」双击：一个 POST、目录里一页。
- 顺带：例行计划的开始 / 结束日期在 HTML 里写死 2026-07-06 → 08-30（设计稿日期），现在开始日期默认今天。

### T2b-2 来回切
- Notebook 切换、Wiki 切页原来就只认最后一次。**没有的四处**：趋势图「日 / 周 / 月」、任务列表、从任务生成的来源列表、参考计划列表 ——
  加了 `latestOnly(key)`；判据在 node 上真跑趋势图（先点「日」后点「月」、「日」后回来，画的还是「月」）。

### T2b-3 失败 / 网慢
- **套用参考计划填错日期：页面上一个字都没有**（控制台一行 Uncaught (in promise)）。两层问题：
  1. 幂等那一层 `catch (Exception)` 把一切包成带原文的业务错误 —— 日期写错回 Java 的「Text '2026-02-30' could not be parsed」，
     真的服务器 bug 把 SQL 原样回给用户、不记运行问题（第十一轮的全接口暴力测试不带 Idempotency-Key，这类 bug 又正好吞掉它找的那条记录）。
     现在原样往外抛，日期错回 400「应当像 2026-09-28」。
  2. 套用、点赞、打卡、删除这些 onclick 没有 catch → 加 `unhandledrejection` 兜底：请求层的错误原样说，代码错误说「没有完成」，
     取消和跳登录时不吭声。真浏览器里：同样的操作现在右上角说「日期 / 时间「2026-02-30」格式不对，应当像 2026-09-28」。

### 暴力测试：每页 1.5 秒随机点 60 多下（任务、例行计划、参考计划、Wiki、统计、个人中心、AI 助手）
- 页面自己的异常 0、服务器运行问题 0。照出三件事，都修了：已结束的例行计划照样给「标记完成」（点了只报错）、「5 个进行中」是写死的、
  同一个空表单的校验提示一会儿「旧密码…；新密码…」一会儿反过来（校验器内部是 HashSet）。
- 看板上有一个按钮本来就跳去任务页，连点脚本在那一页总被带走 —— 是设计如此，不算问题。
- 留给以后：例行计划列表里频率显示的是 `DAILY` 原文。

### 顺带：全量测试每次白等 30 秒
- 开工时猜的「有个非守护线程不退」不对：`System.exit` 本来就不等非守护线程。线程转储（关机时 attach 不上，用 `kill -3`）显示是关机钩子在等：
  关 JVM 时 Spring 在等 RAG worker —— 它卡在一个已经停掉的 MySQL 容器上。根子是 27 个集成测试写的
  `spring.task.scheduling.enabled=false` 不是 Spring Boot 的属性（写了等于没写），定时任务在每个测试上下文里一直跑。
  现在 `app.scheduling.enabled` 是真开关，测试统一关掉。两个集成测试类一起跑：53 秒 → 42 秒、没有强杀、没有结尾那串 EOFException。
- 但全量**还是**被强杀（826 条全绿，5:57）—— 第二个原因，surefire 强杀前自己写了线程转储：`HikariPool.shutdown` 在等「补连接」的线程。
  每个缓存着的上下文的连接池为了保住 minimum-idle，一直往已经停掉的 MySQL 上补连接（退避重试，最长 5 秒一次），
  二十几个上下文关的时候各等一阵。测试里 `spring.datasource.hikari.minimum-idle=0`（没人等连接就不补）。全量 5:57（第十三轮 5:53）→ 5:19，不再被强杀（改之前那一次全量就是它的红）。
