提交：`ddb842f`。（计划文件是第十轮时按当时的工作笔记补存的。）

## 用户的要求（原话）
- 继续优化升级 zhiqu cli 和 zhiqu app 的架构和性能
- 就是提高处理复杂任务的能力和长上下文输入的时候的分析和工作能力
- 还有要提高任务处理的准确率 —— 「叫它干一个活不要一直偏离然后一直修正，最好能一次就成功之类的」
- 在 cli 输入之后，在显示模型处理之前那个输入框还是会短暂的不见
- 那么 zhiqu 的 windows 上跑的 exe 软件呢

## 查实的问题（证据）
- 输入框「不见」：pty 实录，重画分两次写（先擦再画），等模型时状态行每秒刷新 → 每秒一次输入行消失。
- 粘贴 4 行 → 1 条消息 + 3 条排队（各自一轮）。
- read_file 标「读全了」的依据是 10 万字，agent 再按窗口截断 → 模型只看了一段却被允许整份重写。
- CRLF 文件多行替换永远「没找到」；没找到不给线索；搜索结果去掉了缩进。
- 网页 AI 助手：用户消息所有空白压成一个空格（代码缩进、日志换行全没），超 12000 字静默截断；回答入库也截 12000。
- Windows 脚本：`mvn -o` 新机器必失败、原生命令失败不查退出码（jpackage 默认模块已含 jdk.charsets / jdk.crypto.ec，实测）。

## 做了什么
- A 命令行输入：重画一帧写完 + DEC 2026 同步输出；括号粘贴 + 占位；同批多行合并；MCP 启动时输入框在。
- B 命令行准确率：read_file 按窗口读；替换 CRLF / 近似提示 / 多处行号 / replace_all；搜索保留缩进；打转提醒；系统提示「一次做对」。
- B 复杂任务：update_todos 任务清单（置顶、存会话、未完成推一次）；原话置顶；超长输入落盘分段读；压缩分块滚动 + 原话逐字保留。
- C 网页：UserMessageFit（保留换行缩进、上限随窗口、保留头尾、弹 message.notice）；回答入库 20 万字。
- D Windows 脚本：去掉 -o、Assert-Exit。
