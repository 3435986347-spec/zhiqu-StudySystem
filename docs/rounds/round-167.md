# 第一百六十七轮（2026-11-24）：长活省钱第 2 步——会话记录里清理只记换掉的那几条

[`docs/agent-efficiency-plan.md`](../agent-efficiency-plan.md) 的第 2 步（问题 G）。

## 计划

- 原来每清一次（先清、清截图、压过还超时拿掉最大的）就把整份消息存一遍（`{ type: 'compact', messages }`）：用户那段会话 19 份快照约 2000 万字，记录涨到 28.8MB。
- 清理不改条数，只换几条：记 `{ type: 'clear', length, edits: [{ i, key, message }] }`；真摘要（条数变了）照旧记全量。
- 内存里的那份和记录重放出来的不一定一条对一条（被打断时内存里给悬空的调用做了处理、`/resume` 读回来也处理）：工具结果、带调用的助手消息按调用 id 认（序号对不上按 id 找）；别的只在条数和角色都对得上时才换，对不上就不换——退回没清理的样子，多背一点，不会错。
- 旧记录照读；旧版本命令行读到新记录不认 `clear`，等于没清理过，也不会错。

## 做了什么

- `session.js`：`messageKey`（`t:<调用 id>` / `a:<调用 id…>` / `r:<角色>`）、`applyEdits`（先看原位，再按 id 找；按角色认的要条数也对上；坏的跳过并计数）；`load()` 认 `clear`；`append()` 把 `edits` 里的图也换成引用；`transcript()` 不认 `clear`——只是清理，回放里不再说「这里压缩过一次」（原来每次清理都这么说）。
- `agent.js`：`recordRewrite(ctx, prev)`——条数没变记 `clear`、变了记全量；`clearNow`、摘要没写成只省略旧输出、摘要成功、压过还超时拿掉最大的，四处都走它。顺带修了一处：服务器裁过、这边没东西可压时 `shedLargest` 拿掉的那条原来不记，接回来又回来了。

## 结果

- 基线（第一百六十六轮提交后）CLI 全量 700 过 / 22 跳。
- 新判据 `test/session-incremental.test.js` 8 条全绿；6 处扰动各自见红：总存整份 → 5 红；读时不认 `clear` → 6 红；不按 id 找 → 1 红；按角色认时不看条数 → 1 红（两张截图挨着、错开一位，单靠角色挡不住——专门补的样本）；不看钥匙直接按序号换 → 1 红；`edits` 里的图不换引用 → 1 红。
- 最终 CLI 全量：730 项，708 过 / 22 跳 / 0 失败。
- 回放用户那段会话（本机读、不提交；第 1、2 步的新逻辑按事件顺序重写一份记录到临时目录）：28.8MB → 4.15MB；19 行 `clear` 共 35 万字、2 行真摘要的全量共 56 万字；读回来 330 条和内存里的一致（只差 2 张截图：临时目录里没有图的文件，读回来是「截图文件已经不在了」）。
- 真程序：假网关（照 `HarnessModelGateway` 的 `start` / `delta` / `done`）+ `bin/zhiqu.js -p … --mode auto` 读 24 个文件：记录里 1 行 `clear`（换 9 条，这一行 1323 字），没有整份快照；另起进程 `zhiqu exec resume --last 接着`，发给模型的历史里正好是那 9 段占位。第一次用 40K 窗口、12 个大文件跑时直接过了八成、走的是真摘要（记全量，对的），场景改成 100K 窗口、24 个小文件才走到先清。HOME / ZHIQU_HOME 用临时目录，没调付费模型。（只动命令行，真浏览器暴力测试换成这段真程序测试。）
- 没发 npm、没部署：同第一百六十六轮。
