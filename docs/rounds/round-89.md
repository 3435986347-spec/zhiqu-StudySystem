# 第八十九轮（2026-10-31）：coding agent 的稳定性 —— 干活的请求温度 0、交活之前核对一次；全方位锐评

## 由来
第八十八轮的重跑是官方 4/10（第八十七轮 6/10）。用户 2026-10-31：「先别跑了，这不就说明这个coding agent本身存在缺陷吗？稳定性还不够」，
接着「按这个做第八十九轮，同时对当前的coding agent进行一个全方位的锐评」。

## 摸底
- 同一道题、同一版 agent、同一个模型，三次重跑（第六十九、八十七、八十八轮）里三题时对时错：django-12308 错 → 对 → 错、sympy-23950 对 → 对 → 错、requests-1921 对 → 网络 → 网络。
- **温度从来没设过**：网关给命令行的请求不带 `temperature`（`app.ai.temperature` 配的是空），DeepSeek 用默认的 1.0；
  DeepSeek 文档（api-docs.deepseek.com「参数设置」）对写代码 / 数学的建议是 0.0，那一页没说适用哪些模型。
- **答错的都是一个样子**：自己写的测试过了就交活，没覆盖问题里说的那个情况 —— django-12308 没试带元组键的 JSON 值（`keys must be a string`）、
  pytest-10356 多个基类的 mark 顺序排反、sympy-23950 待修的 `test_as_set` 没过。提示词里有一句「收尾之前对照用户的原话逐条检查」，模型不照做。

## 计划
1. 网关：命令行干活的请求单独设温度（`app.ai.harness-temperature`，默认 0）；供应商不认 temperature（400 里提到它）时去掉它原样重试一次 —— 和「输出上限不认就降一档」同一个套路。
2. 命令行：这一轮改过文件、要交活时推一次核对（例子 / 边界逐条验证、看一眼改动），只推一次；提示词那句收尾检查带上例子和边界。
3. 判据先红；用户给的 key 在验证库里拿真模型冒烟（温度 0 收不收、核对怎么走）；评测十题不跑（花钱的量法问用户）。
4. 锐评写在这一份末尾。

## 结果
- **网关**（`HarnessModelGateway`）：构造器多一个 `@Value("${app.ai.harness-temperature:0}")`；OpenAI 兼容和 Anthropic 两条请求都带它；
  400 / 422 里提到 temperature、还一个字没输出时去掉它重试一次（输出上限不变）；留空就跟 `app.ai.temperature`（`ModelProviderClient.configuredTemperature()`）。
  `application.yml` 和生产模板都加了这一项（`ProdConfigParityTest` 管着）。
- **命令行**（`agent.js`）：`VERIFY_NUDGE` —— 「对照用户的原话：① 例子、每种情况（含边界：空的、重复的、顺序、类型不对的、出错的）都验证过了吗？没验证的补一个测试跑一下；
  ② 看一眼这次的改动（git diff 或重读改过的地方），有没有多改、漏改、把原来的行为改坏；③ 都对上了就直接给结论」。这一轮改过文件（`ctx.turnWrites`，每轮对话从 0 数）、
  模型不调工具要交活时推一次；在问用户问题、最后一轮不推。和「清单没做完」那一句收成一个判断（`pendingNudge`）。
  真模型试出来一个毛病：安静模式下「修好了」那条先打一遍、核对完又打一遍 —— 要推的那条现在先不当结论打出来。
- 判据：网关 2 条新的 + 原来两条加断言（OpenAI / Anthropic 都带温度 0）；命令行 3 条（核对推不推、结论只打一遍、提示词），原来「截断」那条的请求数 3 → 4（多的那次就是核对）。
  扰动：网关 5 处、命令行 8 处，全红。plan 档本来就写不了文件，「plan 档不推」那个条件照不出任何东西，删了。命令行 266/266。
- **真模型冒烟**（用户给的 key，验证库，模型 ID 23）：「average / spread 传空列表都报错，修好，spread 单元素返回 0，补测试跑一遍」——
  44 秒、6 轮；核对推了一次，模型跑了 `git diff`、逐条对了三种情况和原来两条测试，5 条全过；网关日志里没有「不认 temperature」（DeepSeek 收下了 0）。
- **没做的**：稳定性有没有真的变好，这一轮没量 —— 要同一题跑好几遍才分得清（第八十八轮就是吃了「一遍两遍下结论」的亏），花钱，问用户。

## 锐评（2026-10-31，对着代码和三次评测说话）

**一句话**：工程纪律是真的（判据见红、一致性用例、隔离严格的评测、照实记账），但 agent 本身还是「一个模型 + 一堆补丁」，
可靠性没有被设计出来，是一轮一轮被事故推着补出来的；而用来判断补丁有没有用的尺子太短，量不出它想量的东西。

### 1. 可靠性：最基本的旋钮八十多轮没碰过
- 温度从来没设，写代码一直在 1.0 上采样。同一题三次重跑三题翻转，这不是「模型的事」，是我们把随机性开到了最大。
- 没有「交活之前对照需求核对」的环节，直到这一轮。答错的题都死在同一个地方：自己的测试过了就宣布完成。提示词里写了「逐条检查」，模型不照做 —— 写在提示词里的规矩基本等于没写。
- 一题只跑一次就下结论。第八十八轮拿两遍、一个问题的真模型对比说「轮数和 token 少了将近一半」，评测十题完全没复现。这是我的问题：测量没设计好就开始改。

### 2. 工具：好用之前先「危险」过
- `write_file` 一个工具三种用法（整份 / 追加 / 替换），参数互相打架；`old_string` + `content` 被当成「换成空」，一声不响删代码，评测记录里 19 次，
  pytest-5840 因此改坏 51 条测试 —— 这个错从工具诞生活到第八十六轮。工具接口的设计应当让错的调用不可能发生，而不是靠事后加拒绝。
- 扩展名白名单、`python3 -c` 禁令、git 禁令：每一条都有道理，合起来让模型每题白花好几轮绕路（第八十六、八十七轮才放开）。安全规则是按「服务器端」想的，套到了用户自己电脑上的命令行。
- 子进程 `HOME` 设成工作区：本意是隔离，结果仓库里带的 `.gitconfig` 能让 git 叫起任意程序（第八十七轮这台机器上试出来的）。npm 读 `~/.npmrc` 是不是同样的口子还没查过。
- 终端里命令输出只给尾巴：`git diff` 用户只看到最后一段。

### 3. 「提醒汤」：越补越多的附一句
- agent 循环里已经有 8 种「附一句 / 推一句」：长篇推测、连续只看、接着往下挪、收尾、连续改不成、连续跑不过、清单没做完、交活核对。每一种都有判据，但彼此的叠加没人测过
  （比如快到上限时收尾提醒 + 核对 + 清单一起来，是不是把最后几轮都耗在被提醒上）。第八十八轮的两种在评测里看不出作用。
- 这说明方向有问题：靠在工具结果后面贴小字去纠正一个大模型，效果弱且不可预测。真正起作用的都是「改了做事的结构」—— 拒掉错的调用、隔离配置、给工具更好的接口。

### 4. 上下文和成本：每一轮重发整段对话
- 没有利用前缀缓存（网关不传缓存命中数，broker 的记账全按未命中价，保守口径比真实账单高几倍）。
- 轮数直接决定成本和能不能做完，但 agent 没有任何「这一步值不值得」的判断，轮数控制只有一个硬上限加一句提醒。

### 5. 评测：严格得令人敬佩，但小得没法用
- 隔离、账本、能力撤销、官方评分、事先写进配置的规则 —— 这套比很多公开评测都严。但：只有 10 道 Python 题，其中 2 道在这台机器上因为网络过不了（分母实际是 8）；
  每题一遍；只测过一个模型（deepseek-v4-pro）。用它判断「改动有没有用」，统计上几乎没有分辨力：6/10 和 4/10 的差在单题翻转的范围里。
- 一次十题 ¥30、半小时；要分出 2 题的差得每题跑几遍 —— 这把尺子贵且短，导致改动只能「凭感觉」上。Java / JS 的补充题集设计了从没建。
- 网关失败时说不出原因：桌面后端不写日志文件，django-15987 那次 `upstream_error` 到底是什么，没人知道。

### 6. 两份 agent
- 命令行（JS）和网页 code agent（Java `CodeWorkspaceAgent`）是两套循环、两套工具，靠一致性用例对齐一部分规则；第八十六轮的删代码错两边都有。
  命令行这几轮放开的东西（行内代码、git、绝对路径、核对、温度）服务器端都没有 —— 两份 agent 的行为正在分叉。

### 7. 做得对的
- 改动都有判据，判据都见过红；扰动绿了会追到「是哪一道防护替它挡了」。
- 写东西先成草稿、工作区默认关、子进程不继承环境变量、密钥不落盘 —— 安全的默认值是对的。
- 评测的协议（事先写进配置、失败照实记、不挑最好的一次）是诚实的；三次重跑的结果都照实写了，包括难看的 4/10。

### 接下来最值得做的（按值得的程度）
1. **先把尺子做好**：一组便宜、可重复、本机就能跑的小题（带隐藏测试，覆盖边界情况），每题跑 3–5 遍算通过率和方差；改动先在这上面过，再上贵的 SWE-bench。
2. **量这一轮**：温度 0 + 核对，拿上面的尺子或者那三道时对时错的题各跑几遍，看翻转是不是少了。
3. **工具接口收窄**：`write_file` 拆成「写整份」「替换一段」两个工具，参数各自必填，错的组合从接口上就不存在。
4. **减提醒、加结构**：把效果看不出来的提醒（第八十八轮那两种）在尺子上量一遍，量不出作用就删。
5. **前缀缓存**：网关把缓存命中数传出来、按命中价记账；轮数多的题成本会降几倍。
6. **两份 agent 收成一份**，或者至少让网页 code agent 跟上命令行这几轮的改动。
