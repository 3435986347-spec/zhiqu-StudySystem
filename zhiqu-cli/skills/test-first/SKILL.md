# 先写测试

用在新功能和补测试上。**修 bug** 时的回归测试在 `debug` skill 的最后一步，那边管的是先复现再修。

## 0. 先认项目用的是什么

不要引入新框架。按这个顺序找：

- `read_file` 读 `package.json` 的 `scripts.test`、`pom.xml` 的 surefire 配置、`pyproject.toml`、`Makefile`、`go.mod`。
- `list_files` 看测试放在哪：`test/`、`src/test/`、`__tests__/`、`tests/`、`*_test.go`。
- 读一个**已有的**测试文件，照它的写法来（导入方式、断言库、fixture、临时目录怎么建）。风格不一致的测试比没有测试更麻烦。

跑一次现有测试，确认基线是绿的。基线本来就红，先告诉用户，不要在他的红上再叠一层。

## 1. 先写测试，并且看着它红

- 一次只加一条，跑它，**确认它因为断言失败而红**。
- 因为 `import` 找不到、语法错、fixture 没建好而红，不算 —— 那说明测试本身还没写对，先修测试。
- 红的时候看一眼失败信息：它有没有说清「期望什么、实际什么」。说不清就改断言的消息，这条测试以后会救你一次。

## 2. 再写实现

- 只写让这条测试变绿需要的东西，不要顺手把「以后可能要用」的也写了。
- 绿了之后先跑整个测试文件，再跑整个套件。

## 3. 断言的质量

一条测试只验证一件事，名字要说清「什么坏了」：

- 好：`拒绝空标题的任务`、`并发提交同一张单只会成功一次`
- 差：`test create`、`test2`

要避免的假测试（跑了等于没跑）：

- 没有断言，只调用一下看它不抛异常。
- 断言恒真：`assert.ok(true)`、`assert(x === x)`、把期望值写成被测函数算出来的值。
- 全部用 mock：mock 返回什么就断言什么，把被测代码删掉测试照样绿。
- 只断言「调用了几次」，不断言结果对不对。

边界至少覆盖：空、只有一项、重复、超长、出错路径。用户提过的那个具体例子，必须有一条测试就是它。

## 4. 收尾

- 测试文件放在项目已有的位置，命名跟邻居一致。
- 回答里给出跑测试的命令和实际输出（几条通过、几条失败），不要只说「测试通过了」。
