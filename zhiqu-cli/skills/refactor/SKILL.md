# 重构

重构的定义：**外部行为一点不变**，只改内部结构。要顺带改行为，就先重构、验证、再改行为 —— 两次分开做，出问题才知道是哪一次。

## 1. 先建基线

- 跑现有测试，把结果记下来（几条通过、哪几条本来就红）。
- 没有测试覆盖要动的地方：先写几条**特征测试**（characterization test）—— 不判断对错，只把当前输出钉住，比如拿几个真实输入跑一遍，把结果写成断言。它和 `test-first` 那种「先写一条会红的测试」不是一回事：这里要的是**现状**，不是期望。
- 至少要能回答：「改完之后，我怎么知道行为没变？」

## 2. 找出全部受影响的地方

- `search` 找符号名，**包括字符串、配置、模板、文档、测试**里出现的。只改定义不改调用处，是最常见的半成品。
- 动态引用（反射、`getattr`、`eval`、依赖注入按名字、路由表、SQL 里的列名）`search` 找不到，要单独想一遍。

## 3. 小步走，每步都绿

一步 = 一个能独立解释的改动：

- 只改名，不改结构；
- 只提取函数，不改逻辑；
- 只移动文件，不改内容。

每步之后：编译、跑测试、至少跑一次相关的那几条。**红了就退回这一步**，不要「先往下改，最后一起修」—— 到那时已经分不清是哪一步坏的。

## 4. 别在同一轮里做的事

- 重命名 + 重排格式 + 改逻辑。三件事混在一起，review 的人看不出哪一行是行为变化。
- 顺手升级依赖、顺手改无关文件的风格。这些单独说，用户同意再做。

## 5. 收尾

- 跑完整测试套件。
- 读一遍自己的 diff（`git diff` 是只读命令，可以跑）：有没有留下注释掉的旧代码、调试打印、没用到的导入、改了又改回去的空行。
- 回答里说清：结构上改了什么、行为为什么没变、靠什么验证的。
