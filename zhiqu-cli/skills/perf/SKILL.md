# 性能

没有测量的优化都是在赌。顺序：测量 → 定位热点 → 改一处 → 再测。

## 1. 先把「慢」变成数字

- 问清楚：哪个操作慢、多慢算慢、数据量多大、在什么环境。用户说「很慢」时，先量出来是 200ms 还是 20s —— 差两个数量级，方向完全不同。
- 计时要在**用户抱怨的那一层**量：接口慢就量接口，不要量一个内部函数然后说「它很快」。
- 跑三次取中位数，避开冷启动和 JIT。第一次总是慢的。

## 2. 找热点

按命中率从高到低看：

1. **N+1 查询**：循环里查库、调接口。`search` 找循环体内的 `query`、`find`、`select`、`fetch`、`http`。
2. **算法**：嵌套循环、循环里 `contains` / `indexOf` / `filter`（列表转 set 通常就够）、重复排序。
3. **重复计算**：同一个值在循环里反复算、正则每次重新编译、配置每次重读。
4. **I/O**：一次读一行、每行一次写、小包多次网络请求、没分页的查询。
5. **内存**：一次性把大结果集全读进内存、缓存没有上限、大对象长期持有。

工具优先用项目里已经有的：`EXPLAIN`（SQL）、`console.time` / `time.perf_counter`、语言自带的 profiler。不要为了测一次性能去装一堆依赖。

## 3. 改一处，再测

- 一次只改一个地方。改三处然后变快了，你不知道是哪一处起作用，也不知道另外两处是不是白改。
- 改完用同样的输入、同样的环境再量一次，把**前后数字**写出来。
- 变慢了或者没变，就退回去 —— 留一个没用的「优化」比不优化更糟。

## 4. 别做的事

- 在没有测量的情况下加缓存。缓存会带来失效、内存、并发一致性问题，通常比原来的慢更麻烦。
- 为了快牺牲正确性（去掉校验、放宽事务、把写操作改成异步）—— 这属于改行为，要单独和用户确认。
- 微优化（少一次函数调用、字符串拼接换 `StringBuilder`）在热点不在这里时毫无意义。

## 收尾

回答里给：原来多少、现在多少、改的是哪里、为什么这里是热点、引入了什么取舍（内存换时间、缓存一致性）。
