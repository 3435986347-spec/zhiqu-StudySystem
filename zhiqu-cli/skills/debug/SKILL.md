# 排查 bug

顺序不能跳。跳步的典型表现是：看了一眼报错就猜一个原因，改一处跑一次，改到第五处才发现方向全错。

## 1. 先把现象变成一条可重复的命令

- 拿到确切的触发方式：哪条命令、什么输入、哪个环境。用户只说「打不开」时，先问清，或者自己找到入口。
- 复现一次，把完整输出留下来。**复现不了就先解决这件事** —— 缺的是环境、数据、顺序、平台，还是缓存？把缺的条件找出来，不要凭想象改代码。
- 报错里最先要看的是**最内层的原因**（Java 是第一条 `Caused by`，Python / JS 是堆栈最底下那条），以及调用栈里**你自己代码**最靠上的那一行。框架内部的帧先跳过。

## 2. 定位到具体位置

- 用 `search` 找报错原文、函数名、配置键，确认是哪一份文件（同一个名字可能有好几处）。
- `read_file` 把那一段连同上下文读完，不要只读报错指向的那一行。
- 需要知道运行时真实的值：临时加一行打印，或者写一个最小的脚本单独跑那条路径。临时文件用完用 `delete_file` 删掉。

## 3. 缩小范围，而不是猜

每次只动一个变量，按顺序试：

1. **二分输入**：把出问题的输入砍一半，看还坏不坏。数据问题通常三步内能定位到具体那条。
2. **二分代码**：在中间位置加打印或者直接返回，判断问题在之前还是之后。
3. **最小例子**：只留必要的依赖。最小例子还能复现，问题就在它里面；不能复现，问题在环境或调用顺序。

## 4. 形成假设，用一次能推翻它的实验去验

- 说得出「如果是 X，那么 Y 应该是 Z」才叫假设。说不出就先别改代码。
- 实验要能**证伪**：跑出来和预期一样，不代表假设成立；跑出来和预期不一样，假设就错了，立刻换。
- 同一处改到第二次还不对，停下 —— 重读代码，检查那个前提：这段代码真的在跑吗？跑的是刚改的版本吗（构建缓存、旧的 class 文件、没重启的服务、装的是全局那份而不是本地那份）？

## 5. 修根因

- 修的是「为什么会这样」，不是「让这个报错消失」。加 `try/catch` 吞掉异常、加一个空判断挡住崩溃，只是把问题推给下一个调用方。
- 改动尽量小，不要顺手重构 —— 那会让「是不是我改坏的」变难判断。

## 6. 留一条会变红的回归测试

- 先确认这条测试在**修之前是红的**（把修复临时撤掉跑一次，或者心里清楚它断言的就是刚修的行为）。
- 断言写在用户能看到的行为上，不要断言内部实现细节。
- 最后跑一遍完整测试，确认没碰坏别的。

## 收尾

回答里说清：根因是什么（一句话）、改在哪个文件哪一行、怎么验证的、还有没有同类地方没改（用 `search` 找过一遍再说没有）。
