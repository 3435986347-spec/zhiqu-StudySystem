# 安全审查

只报**说得清怎么被利用**的问题。说不出利用路径的，放进「存疑」，并标明需要什么条件才能确认。

这里做的是**对一个入口或模块做系统排查**。用户只想看「这次改动有没有安全问题」→ 让他跑 `/review`（P0 里本来就包含安全漏洞），不要两边各报一遍。

## 逐项核对

对每个入口（HTTP 接口、命令行参数、文件上传、消息队列、第三方回调、Webhook）问三件事：**谁能碰到它、它信任了什么、信任错了会怎样。**

### 1. 注入

- SQL：字符串拼接、模板字符串进查询。`search` 找 `"select`、`+ "where`、`${` 靠近 SQL 的地方；ORM 的 `raw` / `query` / `execute` 也要看。
- 命令：`exec` / `system` / `Runtime.exec` / `child_process` 里拼了外部输入。参数化的 `execFile` / `spawn` 传数组才安全。
- 模板与表达式：用户输入进了模板引擎、`eval`、`Function`、SpEL、OGNL、`pickle`。
- 日志注入：用户输入直接进日志，换行符能伪造日志行。

### 2. 鉴权与越权

- 每个「按 id 取数据」的接口：有没有校验这条数据属于当前用户？只查 `where id = ?` 不查 `user_id`，就是水平越权。
- 管理接口有没有独立鉴权，还是只靠前端不显示按钮。
- 批量接口（一次传多个 id）要逐个校验，不能只校验第一个。

### 3. 密钥与凭据

- 仓库里搜 `password`、`secret`、`token`、`api_key`、`AKIA`、`-----BEGIN`。硬编码的一律报。
- 密钥有没有进日志、进异常堆栈、进前端 bundle、进 URL 查询参数。
- 默认口令、默认密钥、示例配置里的占位值（`changeme`、`admin/admin`）有没有被带进生产。

### 4. 路径与文件

- 用户给的文件名拼进路径：`../`、绝对路径、软链、Windows 的 `..\`、URL 编码过的 `%2e%2e`。
- 上传：类型只看扩展名、大小没上限、存到能被执行或能被直接访问的目录。
- 下载与解压：zip slip（压缩包条目名里带 `../`）。

### 5. 反序列化与外部请求

- 不可信数据进 `ObjectInputStream`、`pickle.loads`、`yaml.load`（不是 `safe_load`）；`JSON.parse` 之后的原型污染（`__proto__`、`constructor`）。
- SSRF：用户能给 URL 的地方，有没有拦内网地址（`127.0.0.1`、`169.254.169.254`、`10.`、`192.168.`）、有没有跟随重定向。

### 6. 前端

- `innerHTML`、`dangerouslySetInnerHTML`、`v-html` 里有没有用户内容。
- 敏感数据放进了 localStorage，或者放进了前端可见的接口返回。
- 跨域配置是不是 `*` 加 `credentials`。

### 7. 依赖与配置

- 依赖版本有没有明显过旧、锁文件里的实际版本和清单里写的是不是一回事。
- **不要凭记忆报 CVE 编号和「这个版本有某某漏洞」** —— 这里通常没有外网，编出来的编号比不报更糟。版本明显老就说「版本停在 X，去查一下有没有已知漏洞」，把判断交回用户。
- 生产配置里 `debug`、详细错误页、actuator / 管理端点有没有对外。

## 每条怎么写

```
[高危] src/file/DownloadController.java:63 — 文件名直接拼进路径
利用：请求 ?name=../../../../etc/passwd 能读到工作区外的文件。
修法：先 normalize，再校验结果仍在允许的根目录下（startsWith 要带分隔符）。
```

- 严重度：高危（能直接拿到数据或执行代码）/ 中危（需要登录或特定条件）/ 低危（信息泄露、加固建议）。
- 修法要给出具体位置和判断条件，不要只说「加校验」。

## 收尾

按严重度排序。一条都没有时，说清核对了哪几类、看了哪些入口。**不要用「建议加强安全意识」凑数。**
