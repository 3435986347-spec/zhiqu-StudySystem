# 模块体检

审查**已经存在的代码**。它和 `/review` 分工不同，先认清走哪条：

- 用户要看的是**一次改动**（刚改完、未提交、某个分支的 diff）→ 让他跑 `/review` 或 `zhiqu review`。那条路自己取 diff、在单独的上下文里按固定结构出结论，比在这里做准，而且能接着说「修第 1 条」。
- 用户问的是「这个模块 / 这个文件现在有没有问题」→ 用这个 skill。`/review` 的规矩里明确写了不报改动之前就有的问题，这里报的正是那些。

两件事不要混着做，也不要两边各报一遍。

## 怎么读

- 读完整文件，连同调用方和测试一起看。一段代码对不对，取决于它周围的错误处理、锁、事务、生命周期。
- 先弄清这段代码的契约：输入从哪来、可不可能为空 / 空集合 / 超大、谁负责释放、失败了谁收尾。契约不清就先说「这里没有明确契约」—— 那本身就是问题。
- 项目自己的约定优先于你的偏好：看相邻文件怎么写（错误类型、日志、返回结构），不符合它自己的约定才算问题。

## 找什么（和 diff 审查不同的地方）

1. **错误处理缺口**：每个 `catch`、`if err`、返回码，都问一句「出错了之后，状态还一致吗」。吞掉异常、只打日志不返回、把具体错误降级成通用 500，都算。
2. **资源与生命周期**：文件、连接、事务是不是在所有路径上都关掉了（包括提前 return 和抛异常）；缓存有没有上限和失效。
3. **并发与共享状态**：可变字段被多线程 / 多请求共用、先查后改没有原子性、锁的粒度盖不住读改写、异步回调里用了闭包捕获的旧值。
4. **边界与校验**：外部输入在进入核心逻辑前有没有校验；空集合、只有一项、重复、超长、负数、时区、精度。
5. **重复与分叉**：同一段逻辑出现在两处，改一处漏一处；复制粘贴之后只改了其中一份的条件。
6. **死代码与误导**：永远进不去的分支、注释和代码说的不是一回事、名字和实际行为不符。这类算 P3，但它会让人改错地方，值得说。

安全类问题（注入、越权、密钥、路径穿越）不在这里展开，见 `security-review` skill；性能问题见 `perf` skill。

## 每条怎么写

```
[P1] src/order/service.js:142 — 退款失败时订单状态不回滚
为什么：refund() 抛异常后，前面已经写了 status=REFUNDING，没有事务包住，订单会卡在这个状态，用户既退不了款也取消不了。
怎么改：把这两步放进同一个事务，或者失败时显式回写原状态。
```

- 优先级和 `/review` 用同一套：P0 必须马上修（丢数据、安全漏洞、主流程崩）、P1 合并前要修（常见场景出错）、P2 应该修（边界条件）、P3 小问题但确实是错的。
- 行号要准。说错一个行号，后面的话都会被打折。
- 「为什么」要给一个**具体场景**（什么输入、什么顺序会出事），不要写「可能有问题」。
- 「怎么改」要能直接动手，不要写「建议优化」。

## 收尾

- 按 P0 → P3 排序。
- 一个问题都没有就说「没发现会导致故障的问题」，并说清看了哪些文件、哪些路径没覆盖到。**不要为了显得认真而凑数。**
- 不要顺手改代码 —— 先出结论，等用户点头。用户本来就说了「顺便修掉」的，按结论修，但先说清要动哪几处。
